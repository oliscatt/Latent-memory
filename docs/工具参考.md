# 工具参考：八个 `latent_` 工具怎么调

> 给写宿主、自建前端，或想手工调工具的人。每个工具一节：参数、回执、边界。
> 它们在链路里的位置见[《原理与架构》](原理与架构.md)；日常用户不用读这份，模型会按工具描述自己调。

默认工具表就是这八个。开 `--passive-recall` 时多一个模型可见的 `latent_fact_backfill`（建事实库，
见[《自动浮现》](自动浮现.md)“事实模式”）；开 `--admin-token`（山屋）时多一个 `latent_note_reply`（回便条，见文末）。
隐藏入口 `latent_passive_recall` 只给宿主 hook，不在这份里，见[《自动浮现宿主接入》](自动浮现宿主接入.md)。

所有回执都是给模型读的文字。参数不合格时回执附同类最小对照（“写错／写对”两行），照它改字段，
不要把报错重试冒充预检。`latent_append` 与 `latent_supersede` 都可以先加 `"mode":"preflight"` 零写入地校验一遍。

## 换窗召回：`latent_session_start`

一场会话开始时调一次，没有参数。返回按这个顺序拼成一段：

1. 【对方写给你的便条】：开了 `--admin-token` 且有还没回的便条时才有，排最前；
2. 【当前未解决】：`未解决.md` 里仍没结束的事，并提示由模型自己选合适的时机提起；
3. 【上次会话】：上个窗口 `latent_thread_close` 留下的历史快照，明确标作过去的状态；
4. 【最近记忆召回】：按时间新鲜度与用进废退权重挑出的几段，每段带发生日期；同类相关的记忆以日期最近的一条为当下状态。

它只在开场做一次，不是逐轮自动浮现。空库返回一句“记忆库还是空的”，那是新库的正常状态，不算错误；
读取或解析异常会自动重试一次，仍失败则返回非空 `isError` 与失败类型，不会合法地返回空文本。
开了 `--admin-token`（山屋）时，每次递出在 `<corpus>/.recall-log.jsonl` 记一行（时间、触发方式、召回块的 recordId 与分数，
不含正文），只留近七天，给拍立得看；没开页面不写，写不进去也不影响召回。换窗召回不花任何向量调用：没有查询向量要算，三条检索路线在这一步的代价一样。

## 检索：`latent_search`

| 参数 | 说明 |
|---|---|
| `query` | 必填，要查什么 |
| `queryVariant` | 可选。第一次查不到或明显对不上时，保留原 `query`，把更具体的说法（补名字、物件、地点，或记录里可能用过的词）放这里；服务端融合两路结果，原查询两票、改述一票，最终 topN 才加一次权重。最多再查这一次，不循环查到有为止 |
| `topN` | 返回几条，默认 5 |

返回带来源与日期的片段。命中的记忆权重上升（用进，不废退），这是读类工具里唯一会落盘的动作。
默认只返回现行记录；查询含“以前”“曾经”“搬家前”“变迁”等历史意图，或可靠词面在同一条变迁链上命中多个
recordId 时，整链按登记时间正序返回。**检索返回了东西不等于那就是答案**：现行实现不能可靠判断“库里根本没有”，
对不上就说没找到，不拿沾边的记录去圆（判据与数字见[《快速上手》§5](快速上手.md#5-三条检索路线初始化第-5-步选的就是它)）。

一条可靠候选都没有时返回 `isError`，正文都以“没有可靠命中”开头，分两种说法：

- **问法太泛**：问法里的词库里都有，而且全都太常见（每个都出现在超过 max(3, 块数÷5) 块里，比如两字问法只切出一个词，写入又把它推过了线），候选闸分不出是哪一条。这时说“问法太泛”，并写明“这不等于库里没有这件事”；第一次查提示在 `queryVariant` 里补一个人、地、物、事或日期这类具体的词，已经带过 `queryVariant` 就叫停。
- **其余情况**（问法里的词库里一个都没有，或者常见词＋库里从没出现过的细节——编造的问法多半是后一种）：仍是“记忆库里没有与这个说法词面或语义相关的记录”。

两种只是说法不同，放行规则和排序都一样。

## 写回：`latent_append`

模型或第三方宿主不再自行拼日期、粗体、换行和“两行四段”。只需给正文、当下状态，以及从
二者逐字摘出的证据片段；服务端负责统一生成索引：

```json
{
  "text": "下次想去看企鹅漫步。最好挑个凉快的早上。",
  "current_state": "新约定，档期还没定",
  "unresolvedOps": [
    {"action": "open", "summary": "企鹅漫步的档期还没定"}
  ],
  "indexEvidence": [
    {"type": "event", "quote": "下次想去看企鹅漫步"},
    {"type": "reason", "quote": "最好挑个凉快的早上"},
    {"type": "state", "quote": "新约定，档期还没定"}
  ]
}
```

想先确认参数、绝不写盘时，在同一份参数里加 `"mode":"preflight"`。预检复用实际写入的
正文、原文证据、旧摘要和未解决项校验，并返回预计窗口、文件、`recordId`、`indexStatus` 与
`preflightStatus=ready`；通过后删除 `mode`（或改成 `write`）再调用。写入时会重新校验，
预检结果不是跳过校验的确认令牌。工具整体仍有写入能力，因此 annotations 继续标为非只读。

参数错误会在同一条工具回执中给同类最小对照，例如：

```text
索引证据无法映射回原文……
写错：{"indexEvidence":[{"type":"event","quote":"她计划下周复查"}]}
写对：{"indexEvidence":[{"type":"event","quote":"她说下周要去复查"}]}
```

定位失败时这条回执还会附上原文里最接近的一段（含前后文），照着它逐字改就行，不必为了抠字
再拉一次原文。

预检不带 `indexEvidence` 也可以通过，但会明确返回 `indexStatus=pending`；这表示正文参数合法、
真正写入后仍需按回执里的 `recordId` 补索引，不等于索引已经就绪。

`unresolvedOps` 在兼容模式下可省略：旧客户端的正文仍会保存，但回执会明确给
`unresolvedStatus=not_reviewed`。新调用应显式给 open／update／close，或无变化时传
`[{"action":"none"}]`。要让缺字段在写盘前直接失败，服务端启动参数加
`--require-unresolved-review`；这只卡字段缺失，清单文件损坏仍不会吞掉正文。

`type` 只取 `event`／`feeling`／`reason`／`state`／`context`。服务端容忍空白、全半角和
中英文引号／标点形态差异，但不接受同义改写；最终写进 index 的是服务端重新定位出的原文。
证据失败时正文仍保存，回执形如 `recordId=…，indexStatus=pending`。此后补索引只调用：

```json
{
  "recordId": "此前回执里的16位标识",
  "indexEvidence": [
    {"type": "event", "quote": "下次想去看企鹅漫步"},
    {"type": "state", "quote": "新约定，档期还没定"}
  ]
}
```

补索引时不要再传 `text` 或 `current_state`，否则会被明确拒绝；因此不会为了修索引重复写正文。
补索引同样可先加 `"mode":"preflight"`，确认 recordId 与证据有效且尚未生成索引；预检不会
创建索引文件，已经有索引时会明确返回“无需重复补索引”。

可选的 `window` 指定写进第几个窗口，不给就按当天归窗。可选的 `facts`：工具里有 `latent_fact_backfill`
（部署开了自动浮现）就把这次的新事实一句一条带上，会追加进事实库的 `增量/`；没有就不带。`facts` 格式不对时整次写回被拒，
正文也不写，报错会指出是第几条、哪一项（例如 `facts[2].fact 137 字，要 8～120 字`，按字符数算，一个汉字算一个）；
回执里的 `factsStatus=` 说明事实有没有进库（见《自动浮现》“事实模式”）。可选的 `passive` 写入自动浮现用的
触发词与原文范围等辅助元数据，经原文范围核验后进辅助账本，也可凭同一 `recordId` 分阶段补齐。

## 事实变了：`latent_supersede`

搬家、换工作等场景里，旧值当时是真的，不要用 `latent_correct` 把历史撤掉。先从
`latent_search` 结果取得旧 `recordId`，再把新事实按写回格式交给 `latent_supersede`：

```json
{
  "supersedes": "旧记录的16位recordId",
  "text": "她从云港搬到临川南坡。",
  "current_state": "当前住在临川南坡。",
  "indexEvidence": [
    {"type": "event", "quote": "她从云港搬到临川南坡"},
    {"type": "state", "quote": "当前住在临川南坡"}
  ]
}
```

服务端在 `.supersessions.json` 同时登记旧记录的 `status=superseded／superseded_by` 与
新记录的 `status=current／supersedes`。默认检索只返回 current；带“以前”“曾经”“搬家前”
“变迁”等历史意图的查询，或可靠词面在同一条链上命中多个 recordId 时，会补齐整链，并按 Latent
登记变化的时间正序返回（所以验证变迁时新旧两条别共用区分性词，见[《升级与迁移》“升级后验证”](升级与迁移.md#升级后验证)）。没有 sidecar 的
老语料一律按 current 读取，正文不会被迁移或改写。工具也支持 `mode=preflight`。

新事实已经用 `latent_append` 写进去了、事后才发现它取代了一条旧记录时，不要把正文再写一遍，
改用**只补链**：只传两个 recordId，不带 `text`。服务端只在 `.supersessions.json` 里补这一段链，
不写新正文、不重建索引：

```json
{"supersedes": "旧记录的16位recordId", "by": "新记录的16位recordId"}
```

两条都必须是现行库里的 timeline 记录（索引摘要不算），旧的还没被取代，补上不会成环；
不合要求时报错会写明怎么改，什么都不写。带了 `by` 就不能再带 `text`、`current_state`。

**写入端旧记录提示（默认关）**：设了 `LATENT_SUPERSEDE_HINT_MIN` 与 `LATENT_SUPERSEDE_HINT_LEAD`
两个环境变量后，`latent_append` 写完新记录，会拿它现成的向量和库里现行的 timeline 记录比一次（不发额外请求；和新记录同一天的记录不算，按记录自己的日期——同一天的多半是同一件事接着写，不是旧状态被取代）；
第一名分数不低于前者、又领先第二名不少于后者时，回执末尾附一段 `supersedeHint`，列出那条旧记录的 recordId
和它的当下状态，请 AI 判断：取代了就只补链，不是就什么都不用做。最多列两条，分不开就不提。
两个线没有通用默认值：不同向量模型的分数不是一把尺子，要在自己的语料上量（`tests/supersede_hint_calibration.py`，
只读、不打印正文）。每次提示会在 `~/.cache/latent-supersede-hints.jsonl`（`LATENT_SUPERSEDE_HINT_LOG` 可改）
记一行时间与 recordId，之后收到对应的只补链再记一行，用来看提示被忽略的比例；不记正文，不在语料目录里。

## 记错了：`latent_correct`

| 参数 | 说明 |
|---|---|
| `quote` | 必填，逐字摘自要撤回的那条记录的原文 |
| `reason` | 必填，为什么它从未真实过 |
| `correction` | 可选，更正写成一条新记录 |
| `current_state` | 可选，新记录的当下状态 |

`latent_correct` 只留给“旧记录从未真实过”的纠错。它进入撤回账本，即使历史查询也不会返回；
这条记录写入时带的索引摘要（文件名里带它的 `recordId`）跟着一起退出检索，回执会报出条数。
更正写成新记录、回执给出新 `recordId` 且 `indexStatus=pending`，需要的话按新 `recordId` 补 `indexEvidence`。

### 撤的是一块，不是一件事

`latent_correct` 撤回的是**你逐字摘的那一块记录**（连同这条记录自己的索引摘要），
不是「这件事」。同一个说法如果还写在别的记录里，那些记录**不受影响**——它们没被撤，照常在库里。

这在两条路上的表现不一样，**差别是真实的，不是错觉**：

- **主动检索（`latent_search`）**：按相关性排序，你问「TA 那只狗叫什么」时，
  那些讲别的事、只顺带提到旧名字的记录通常排不上去，所以看起来「已经改对了」。
  ⚠ **但那是碰巧问不到**，换个问法（问那些记录本身讲的事）旧说法照样会回来。
- **换窗召回（`latent_session_start`）**：**没有 query，按时间新鲜度和权重排**，
  没有相关性这一关。**旧说法只要够新或被翻得够多，就会被直接端到模型面前**——
  而那些旧记录的正文里往往就写着「当下状态：……（旧值）」。

**所以：改过重要的事实之后，再用旧说法查一次，把还提到它的记录一并撤掉。**
（召回块开头那句「同类相关的记忆里，以日期最近的一条为当下状态」能兜住一部分，
但那是**交给模型判断**，不是硬保证。）

**服务端会主动提醒你**：`latent_correct` 撤回成功后，会顺手扫一遍库里还有没有
别的块与它共享词面，命中就在返回里告诉你「还有 N 块与它共享词面（最近：……）」，
并给出下一步（可以用旧说法再查一次看看还有没有；**不必、也不该逐条撤**）。
⚠ **它只提示、绝不替你自动撤**——词面命中不等于讲的是同一件事，撤错比给旧值更糟，
这条边界守死。

⚠ **共享词面的块超过全库 20% 时，返回里不再给精确条数**，只说「相当一部分记录与它
共享词面、占比过高、这个数没有定位价值」，那三条定位照旧给。门槛复用的是本项目判断
「一个词面还算不算区分性」的同一个 20%（`_distinctive_df()` 的 `max(3, N//5)`），
**不是标定出来的**。⚠ 它只挡得住并集爆炸那一档（外部报告在真实语料上量到 34.1%）；
占比落在 10%～20% 之间时照样会报出一个没有定位价值的精确数字——**这是「把最坏的一档
挡掉」，不是「修好了」**。

⚠ 这个形状在合成语料上复现过，也确认了 `latent_session_start` 那条路**并没有
漏掉撤回账本**（被撤的那一块确实不会再出现）；漏掉的是**同一个事实的其它块**。

## 精准清理：`latent_cleanup`

`latent_cleanup` 只接受写回回执里的 16 位 `recordId`，不按相似文字、标题或短引文
猜目标。先调用：

```json
{"action": "preview", "recordId": "此前回执里的16位标识"}
```

预览纯读，会返回正文片段、关联索引数和绑定当前文件快照的 `confirmation`。确认确实是要清理的
误写后，再逐字交回令牌并说明原因：

```json
{
  "action": "delete",
  "recordId": "此前回执里的16位标识",
  "confirmation": "preview 返回的完整令牌",
  "reason": "把星期二误写成星期三"
}
```

两次调用之间正文、关联索引或受影响 sidecar 有变化，旧令牌会失效，必须重新预览。未解决清单
仍引用该 `recordId` 时也会拒绝，并点出须先 update／close 的事项 ID。成功前，服务端会把本次
涉及的原始文件保存到 `<corpus>/.cleanup-trash/`：副本用 `.bak`，不会被当成语料重新加载；
`manifest.json` 记录原路径、SHA-256、原因和 UTC 时间。它只清 Latent 自己写下的单条记录，
不提供批量删除，也不替代普通导入语料的 `latent_correct`。事实变迁链上的节点会拒绝直接
清理，避免留下断链；若其中一条从未真实过，使用 `latent_correct` 让它在所有检索中退出。
验证变迁时造的合成记录也一样清不掉，所以变迁最好在语料副本或临时目录上验。

## 未解决清单：`latent_unresolved`（只写不读）

`latent_unresolved` 的 `action` 只有三个值——`open`（往清单里**新增**一条）、`update`（改一条）、
`close`（关掉一条）。**没有 `list`，也没有任何“查看”动作。**

⚠ 最容易踩的一步是拿 `open` 当“打开清单看看”用：它不是读操作，会往清单里写进一条新的未解决事项。

要看当前还未解决什么，调 **`latent_session_start`**——它开场就先给【当前未解决】那一段
（这也是每次新会话本来就该做的第一件事）。清单本身落在语料目录下的 `未解决.md`，直接读文件也行。

## 收尾：`latent_thread_close`

| 参数 | 说明 |
|---|---|
| `window` | 必填，第几个窗口 |
| `current_state` | 必填，窗口结束时的状态 |
| `topics` | 这一窗聊了哪几条线 |
| `open_loops` | 可选的旧字段，只进历史快照，不作为当前未解决召回；当前未解决看 `unresolvedOps` |
| `started_at` | 会话开始时间，省略按 1 小时前 |
| `unresolvedOps` | 显式复核未解决清单：`open`／`update`／`close`，无变化传 `[{"action":"none"}]`；省略时正文照常保存、回执给 `unresolvedStatus=not_reviewed`，服务端加 `--require-unresolved-review` 才拒绝缺字段 |

它把本窗口的历史快照存进 `threads.jsonl`，下个窗口开场作为【上次会话】返回，并明确标作过去的状态，不冒充长期事实。
有宿主的客户端里靠模型自觉在收尾时调；自建前端往往没有“会话结束”事件，用 idle 超时代替（见《注入契约》坑②）。
真漏了也不断线：服务端会从最后几轮自动生成一条收尾，标注“自动生成、未经确认”，不假装是模型确认过的判断。

## 旧写法：`indexSummaries` 的逐字校验规则

新调用优先使用上面的 `indexEvidence`；旧客户端仍可传 `indexSummaries`。兼容校验器按下面的
规则逐字判断，不会替调用方猜意思：

1. `summary` 必须完整匹配
   `^\*\*YYYY.MM.DD\*\*：(A)。\n(B)。\*\*当下：(C)。\*\*$`。报错里的第 1／2／3 段
   分别指 A／B／C，不包含日期段。
2. 证据底稿是 `evidence_base = text + "\n" + current_state`；`current_state` 与正文一样
   参与证据校验。
3. 每个 `evidenceTerms` 证据词必须**同时**是 `summary` 的子串，也是 `text` 或
   `current_state` 的子串。只在正文里有、却没写进摘要，仍然是越界词；只在摘要里有也一样。
4. 比较就是纯子串比较：标点参与，不分词、不认近义词、不忽略虚词，也不做归一化。

此外，A／B／C 每段都至少要含一个合格证据词。格式错误会直接指出不匹配的是 A、B 还是 C；
越界错误会指出该词缺在 `summary`，还是缺在 `text/current_state`。

## 已有语料但索引层是 0 块

绕过 `latent_append`，直接把 Markdown 正文提交进语料目录时，timeline 会有内容，但不会自动
生成索引层。发现方法是用实际配置参数运行 `--doctor`，看“建库”一行：如果叙事层有块、
索引层显示 `0`，正文虽然已进库，检索质量会低一档。

对这种没有 `recordId` 的旧语料，不要重新调用 `latent_append` 把正文写一遍。应在实际配置的
`--index-dir` 下，为已有语料逐份补唯一命名的 `.md` 索引文件；旧部署没配该参数时才放进
`<corpus>/index/`。每份只写从对应正文逐字摘出的高密度证据，不补正文没有的推断，例如：

```markdown
**2026.08.29** · 原文证据索引
事件：拆开发现咖啡机保险丝熔断；换好保险丝后恢复加热
状态：咖啡机已经修好
```

补完再次运行 `--doctor`：判据是索引层块数从 0 变为实际补入数，且拿正文中的一句原话做
检索自查能命中。`README.txt` 只是说明文件，不算索引块；不要为了让数字变绿而复制正文、
伪造摘要或重新初始化现有语料。

## 回便条：`latent_note_reply`（开了 `--admin-token` 才有）

| 参数 | 说明 |
|---|---|
| `id` | 必填，便条开头那个 `N-…` |
| `decision` | 必填，`changed`＝认同、正文已经改好；`declined`＝不改 |
| `reply` | `declined` 时必填：一两句为什么；`changed` 时可选 |

对方在山屋的小锁信里写的便条存进 `<corpus>/便条.jsonl`（只追加）。走 stdio 的进程配了 `--admin-token`（或环境变量
`MEMORY_HTTP_ADMIN_TOKEN`）也开，只是没有页面口子。开场 `latent_session_start` 最先列出还没回的；
认同就先用 `latent_correct`（从来不对）或 `latent_supersede`（后来变了）改正文，再记 `changed`；不认同记 `declined`，
reply 写为什么，对方在页面上看得到。一张便条只回一次。记忆只有 TA 能改，这个工具只记回话，不改正文。
