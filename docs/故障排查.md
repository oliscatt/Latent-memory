# 故障排查

先判断问题在哪一层：进程、传输、工具路由、目录、检索，还是模型服从度。几层的失败形态很像，
但证据不同；不要用“模型还能回话”证明 Latent 已经工作。

## 先跑三步

```bash
# 1. 代码自身
python tests/run_release_checks.py

# 2. 用户目录，只读
python src/mcp_server.py --doctor --corpus <语料目录> \
  --index-dir <索引摘要目录> --threads <threads.jsonl>

# 3. 看当前帮助，确认运行的是这一份源码
python src/mcp_server.py --help
```

报告问题时保存命令、完整错误原文和退出码；删掉 token、真实路径中的身份信息、问句与记忆正文。

## 服务起不来

| 现象 | 先看什么 | 常见出口 |
|---|---|---|
| `python` 找不到 | `python --version` | 安装 Python 3.10+，Windows 也可试 `py` |
| `ImportError` | 是否只复制了单个 `.py` | 使用完整仓库或完整 `src/` |
| 端口占用 | 服务端第一段错误 | 换端口，或停掉真正占用它的旧进程 |
| 非回环绑定被拒 | 是否缺 `--token` | 配 Bearer token；公网再由反代提供 TLS |
| IANA 时区不可用 | Windows 是否有时区数据库 | 安装 `tzdata`，或知情地使用固定偏移 |

## 客户端看不到工具

1. 先在终端直接运行配置里的命令；stdio 服务应保持等待输入，而不是立刻退出。
2. 核对客户端配置中的 Python、server、语料、索引和 threads 都是绝对路径。
3. 核对工具名是否是七个 `latent_` 名称，并确认包含 `latent_cleanup` 与 `latent_unresolved`。
4. HTTP 客户端检查 URL、绑定地址、端口、token 与 `Accept`；stdio 客户端不要填 HTTP URL。
5. 修改配置后完全退出并重开客户端；只关聊天窗口不一定重启 MCP 进程。

## 服务显示已连接，但调用的不是 Latent

这是工具撞名最危险的形态：服务仍连接、工具列表仍有项目、模型仍正常回话，全程可能零报错。
请在客户端的实际工具调用记录里确认名称带 `latent_` 前缀，并检查返回文本是否来自本项目。

不要用“它回答得像记得”当判据；要看工具是否真的被调用。

## HTTP 连接问题

| 状态／现象 | 含义 |
|---|---|
| 服务端一行日志都没有 | 请求没到进程；查绑定地址、防火墙、端口映射与反代 |
| 401／403 | token 缺失、错误，或 Origin 不允许 |
| 404 | URL 路径不对 |
| 405 | 客户端传输形态不符、SSE 长流被关闭，或长流达到上限；以日志原因为准 |
| 411／413 | 请求缺长度或请求体过大 |
| 客户端一直等 | 它可能先建 GET SSE 长流且不会回退；不要启用 `--no-sse-stream` |

正常客户端若只接受 SSE，POST 会拿单事件 SSE；其余接受 JSON。GET 长流只发心跳，不会主动推送
记忆。远程 HTTP 是明文传输，生产环境应由反向代理提供 HTTPS。

### 公网 IP 入站整体不可达

非大陆云主机的公网 IP 可能出现整段入站不可达：ping 全丢、各端口直连都超时，但服务在
主机本地自查正常。这是网络入口问题，不是 Latent 的缺陷。不要在这种情况下反复改 MCP
参数；先让 Cloudflare Tunnel 从主机主动建立出站连接，绕开公网 IP 入站。

先用 `trycloudflare` 临时隧道验证链路；一旦能通，再换成“固定域名＋命名隧道”作为长期
配置。**trycloudflare 给出的临时 URL 每次重启都会变化，不能写进长期客户端配置。**
隧道只解决可达性；公网 HTTP 仍须保留 token，并由 HTTPS 终止层保护。

## 写入成功，但新窗口查不到

依次确认：

1. `latent_append` 返回的绝对写入路径是不是当前 `--corpus` 的 `timeline`；
2. `--doctor` 是否读到新增窗口与正确时间范围；
3. `--index-dir` 是否与写入时一致，避免两套索引分叉；
4. 新会话是否真正调用 `latent_session_start`；
5. 提到过去时是否真正调用 `latent_search`；
6. 查询是否只换了一种更具体的说法；仍对不上就明确说没找到。

写入磁盘、能被检索、模型主动调用是三道不同判据。前一道通过不能替后一道通过。

## 日期错一天或窗口归错日

检查 `--timezone`／`MEMORY_TIMEZONE`。未配置时默认 `Asia/Shanghai`；服务器系统时区不会自动
顶替记忆所有者时区。改准后新记录会按新时区归窗，旧文件不会自动重写。

## 初始化被拦住

ship 闸门的报错会带下一步命令。常见原因包括：

- 原人格有整节消失，未明确 `--accept-persona-drift`；
- rewrite／delete 或硬边界冲突尚未逐节确认；
- `section_version_id` 已过期，需要重新跑 `choose-sections`；
- 导入会覆盖已有 timeline，必须选择备份或明确接受覆盖；
- 检索路线还没由用户选择；
- `--corpus` 指向文件而不是目录。

不要手工复制 preview 冒充 ship；那会连带跳过后续配置、备份与一致性检查。

## Git 显示成功，但云端没有新记忆

如果记忆产出在用户自己的私有 Git 仓库里，写回后应推当前工作分支：

```bash
git status
git push origin HEAD
```

随后还要把该分支合回默认分支。写死 `git push origin main` 时，如果实际改动在任务分支，Git
可能返回 `Everything up-to-date` 和退出码 0，但新记忆一个字都没推上去。

## 仍无法定位

提交最小虚构复现，并附：Latent commit／tag、Python、系统、客户端版本、stdio 或 HTTP、完整
错误原文、是否重启后恢复。安全问题与可能含私人内容的报告按根目录 `SECURITY.md` 走
GitHub 私密漏洞报告；不要上传真实人格、记忆库或导出包。
