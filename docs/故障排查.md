# 故障排查

先判断问题在哪一层：进程、传输、工具路由、目录、检索，还是模型服从度。几层的失败形态很像，
但证据不同；不要用“模型还能回话”证明 Latent 已经工作。

这份步骤默认由拿到仓库的 AI 执行并向用户解释，不要求用户自己跑命令或翻日志。自动浮现问题
先关闭再排查；关闭不会影响主动检索、换窗召回和正常写回。

## 先跑三步

```bash
# 1. 代码自身
python tests/run_release_checks.py

# 2. 用户目录，只读
python src/mcp_server.py --doctor --corpus <语料目录> \
  --index-dir <索引摘要目录> --threads <threads.jsonl>

# 3. 看当前帮助，确认运行的是这一份源码
python src/mcp_server.py --help
```

报告问题时保存命令、完整错误原文和退出码；删掉 token、真实路径中的身份信息、问句与记忆正文。

## 服务起不来

| 现象 | 先看什么 | 常见出口 |
|---|---|---|
| `python` 找不到 | `python --version` | 安装 Python 3.10+，Windows 也可试 `py` |
| `ImportError` | 是否只复制了单个 `.py` | 使用完整仓库或完整 `src/` |
| 端口占用 | 服务端第一段错误 | 换端口，或停掉真正占用它的旧进程 |
| 非回环绑定被拒 | 是否缺 `--token` | 配 Bearer token；公网再由反代提供 TLS |
| IANA 时区不可用 | Windows 是否有时区数据库 | 安装 `tzdata`，或知情地使用固定偏移 |

## 客户端看不到工具

1. 先在终端直接运行配置里的命令；stdio 服务应保持等待输入，而不是立刻退出。
2. 核对客户端配置中的 Python、server、语料、索引和 threads 都是绝对路径。
3. 核对工具名是否是八个 `latent_` 名称，并确认包含 `latent_supersede`、`latent_cleanup` 与
   `latent_unresolved`。
4. HTTP 客户端检查 URL、绑定地址、端口、token 与 `Accept`；stdio 客户端不要填 HTTP URL。
5. 修改配置后完全退出并重开客户端；只关聊天窗口不一定重启 MCP 进程。

## 服务显示已连接，但调用的不是 Latent

这是工具撞名最危险的形态：服务仍连接、工具列表仍有项目、模型仍正常回话，全程可能零报错。
请在客户端的实际工具调用记录里确认名称带 `latent_` 前缀，并检查返回文本是否来自本项目。

不要用“它回答得像记得”当判据；要看工具是否真的被调用。

## HTTP 连接问题

| 状态／现象 | 含义 |
|---|---|
| 服务端一行日志都没有 | 请求没到进程；查绑定地址、防火墙、端口映射与反代 |
| 401／403 | token 缺失、错误，或 Origin 不允许 |
| 404 | URL 路径不对 |
| 405 | 客户端传输形态不符、SSE 长流被关闭，或长流达到上限；以日志原因为准 |
| 411／413 | 请求缺长度或请求体过大 |
| 客户端一直等 | 它可能先建 GET SSE 长流且不会回退；不要启用 `--no-sse-stream` |

正常客户端若只接受 SSE，POST 会拿单事件 SSE；其余接受 JSON。GET 长流只发心跳，不会主动推送
记忆。远程 HTTP 是明文传输，生产环境应由反向代理提供 HTTPS。

### 公网 IP 入站整体不可达

非大陆云主机的公网 IP 可能出现整段入站不可达：ping 全丢、各端口直连都超时，但服务在
主机本地自查正常。这是网络入口问题，不是 Latent 的缺陷。不要在这种情况下反复改 MCP
参数；先让 Cloudflare Tunnel 从主机主动建立出站连接，绕开公网 IP 入站。

先用 `trycloudflare` 临时隧道验证链路；一旦能通，再换成“固定域名＋命名隧道”作为长期
配置。**trycloudflare 给出的临时 URL 每次重启都会变化，不能写进长期客户端配置。**
隧道只解决可达性；公网 HTTP 仍须保留 token，并由 HTTPS 终止层保护。

## 写入成功，但新窗口查不到

依次确认：

1. `latent_append` 返回的绝对写入路径在不在当前 `--corpus` 之内——默认是 `<corpus>/timeline`，
   配了 `--write-dir` 则是它指向的目录；**配到 `--corpus` 外面就是这一节的典型成因**：
   写盘成功、回执正常，而检索只按 `--corpus` 递归，永远读不到它（`--doctor` 判 `✗`）；
2. `--doctor` 是否读到新增窗口与正确时间范围；
3. `--index-dir` 是否与写入时一致，避免两套索引分叉；
4. 新会话是否真正调用 `latent_session_start`；
5. 提到过去时是否真正调用 `latent_search`；
6. 查询是否只换了一种更具体的说法；仍对不上就明确说没找到。

写入磁盘、能被检索、模型主动调用是三道不同判据。前一道通过不能替后一道通过。

## 日期错一天或窗口归错日

检查 `--timezone`／`MEMORY_TIMEZONE`。未配置时默认 `Asia/Shanghai`；服务器系统时区不会自动
顶替记忆所有者时区。改准后新记录会按新时区归窗，旧文件不会自动重写。

## 初始化被拦住

ship 闸门的报错会带下一步命令。常见原因包括：

- 原人格有整节消失，未明确 `--accept-persona-drift`；
- rewrite／delete 或硬边界冲突尚未逐节确认；
- `section_version_id` 已过期，需要重新跑 `choose-sections`；
- 导入会覆盖已有 timeline，必须选择备份或明确接受覆盖；
- 检索路线还没由用户选择；
- `--corpus` 指向文件而不是目录。

不要手工复制 preview 冒充 ship；那会连带跳过后续配置、备份与一致性检查。

## Git 显示成功，但云端没有新记忆

如果记忆产出在用户自己的私有 Git 仓库里，写回后应推当前工作分支：

```bash
git status
git push origin HEAD
```

随后还要把该分支合回默认分支。写死 `git push origin main` 时，如果实际改动在任务分支，Git
可能返回 `Everything up-to-date` 和退出码 0，但新记忆一个字都没推上去。

## stdio 形态下什么都看不到（服务端到底发生了什么）

stdio 传输里 stderr 交给客户端接管，而**很多客户端直接丢弃它**。于是服务端的启动横幅、
被拒记录、异常堆栈全都没有落点：进程崩没崩、什么时候重启的，从外面一个字也看不见。

加 `--log-file` 把这些同时落盘一份：

```bash
python mcp_server.py --corpus <语料目录> --log-file <日志路径>
```

- 文件按**追加**写，不会覆盖上一次。
- **每次进程启动写一行带 pid 和时间的横幅。** 同一个文件里出现第二条横幅，就说明子进程
  确实重启过一次——这是判断“是不是悄悄重启了”最直接的证据，不必再靠回头翻 token 账单
  发现某段 prompt 前缀被重复计费、反推重启。
- 日志写不进去（路径没权限等）不会连累服务：会在终端抱怨一句，然后照常起。

⚠ 它记的是**服务端自己**那一侧。客户端为什么重启这个子进程，要去客户端／宿主那边查。

## 自动浮现问题

### 第一步：先关闭

AI 先把宿主的 `passive_recall.enabled` 改为 `false`（或移除自动浮现配置），停止以
`--passive-recall` 开放隐藏入口，重启适配器，同时保留八个普通 `latent_` 工具。主动检索、
换窗召回 `latent_session_start` 和正常写回完全不受影响；用户不会因关闭丢失已有记忆。

自动浮现检索路径只读记忆库，不改正文、索引、撤回／变迁账本或权重。最坏情况通常是错误或
过期资料留在历史保留模式的对话中。宿主能移除就移除；不能移除时告诉用户旧资料仍可能影响
回答，并新开不继承旧片段的会话。不要声称关开关已经物理删除历史。

### 第二步：由 AI 分层读取信号

| 阶段 | AI 要核的证据 | 不能推出什么 |
|---|---|---|
| 宿主能力 | hook 是否在用户消息之后、首个模型请求之前；返回能否进本轮输入；是否控制 history | 支持 MCP 不能推出三项成立 |
| 隐藏入口 | 服务端是否以 `--passive-recall` 启动，宿主能否调用 `latent_passive_recall` | 入口可调用不代表有候选 |
| 候选 | 状态是 `ready`／`candidate`／`empty`，原因码是什么 | 空结果不一定是故障 |
| 注入 | 宿主实际请求是否确认带入同一 delivery 的已组装资料 | 取得候选不等于完成注入 |
| 模型表现 | 注入后是否自然使用、是否接受纠正 | 没接梗不等于服务坏了；说“想起来了”也不是调用证据 |
| 生命周期 | 保存、恢复、分叉、压缩、取消和重启后是否重复或残留 | 单轮通过不能替长期历史正确性背书 |

AI 排查完要输出《自动浮现》规定的部署报告：hook 时机、名称与执行点、模式、隐藏入口、候选、
注入和一句话关闭方法。不确定项照实写“未确认”，不让用户自己去找日志中的成功信号。

### 第三步：反馈

普通故障走 GitHub“自动浮现问题”表单；跑通或跑不通的宿主记录走“自动浮现宿主兼容性”表单。
五项必填：Latent 完整 commit、宿主名称与版本、hook 执行时机、当前模式、实际结果与预期结果。
操作系统、Python、传输、模型、base、生命周期证据、最小虚构复现和脱敏日志全部可选。

禁止上传真实人格、记忆正文、问句、回答、token、私人路径或原始导出包。安全问题按根目录
`SECURITY.md` 走 GitHub 私密漏洞报告。

初期不承诺响应时间。处理优先级是：数据损坏或不可恢复风险 → 跨用户读取／未授权访问 →
凭证问题 → 错误资料持续进入历史 → 接入失败 → 没有浮现或自然效果不理想。

## 仍无法定位

由 AI 整理 Latent commit／tag、Python、系统、客户端版本、stdio 或 HTTP、完整错误原文、
是否重启后恢复。最小虚构复现与脱敏日志有帮助，但不是提交门槛；stdio 形态能安全复现时，
AI 可先加 `--log-file` 收集服务端记录。安全问题与可能含私人内容的报告按根目录
`SECURITY.md` 走 GitHub 私密漏洞报告；不要上传真实人格、记忆库或导出包。
