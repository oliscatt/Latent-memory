# 快速上手

> 给拿到这个项目、想把自己的 AI 记忆接起来的人。只讲下一步敲什么；
> 为什么这么设计见仓库 README 的「几条贯穿全项目的设计判断」一节。

## 需要什么

- Python 3.10+（全程零第三方依赖，不用 pip install 任何东西）
- 一个支持 MCP 的客户端。维护者实测过的：**Claude Code**（桌面端与云端线程都跑通）、
  **Codex**（桌面端跑通；**云端线程验过了，当不了日常对话窗口**，见 §3b 末尾）、
  **Claude 桌面 App**，以及通过 VPS 远程 MCP Connector 接入的 **claude.ai 网页／手机 App**。
  **Kelivo、Operit 两个闭源手机前端也实测过**，成色边界见 §3c。
  **Grok 分三个入口记成色、互不借用**（详见 §3c）：**grok.com 网页 Connector** 有一例外部实测接通，
  ⚠ 但它**强制 OAuth 发现（AS metadata／PKCE）、纯静态 Bearer 点不了「保存并连接」**，
  那位用户是自建最小 OAuth shim（**用户侧扩展、非本项目功能**）才接上的；
  **Grok Build（CLI）** 只有产出格式接上（`--client grok`），没有真机跑通证据；
  **xAI API／Remote MCP Tools** 官方文档证明有入口，**本项目无实测**。
  **ChatGPT 已完成一例真机读链路接入**：Secure MCP Tunnel 能把本机 MCP 接进开发者模式，
  不用开放公网入站端口；State Ledger 部署已在 ChatGPT Work 新窗口成功调用 `state_session_start` 并读取跨窗便签，见 §3c；这不替代本项目 `latent_*` 工具的逐项验证。
  其它聊天端仍需逐家确认支持状态。**自己写的前端也能接**，见 §4b 与《注入契约》。
  维护者已经在真实生产自建前端上跑通一例“借宿主引擎”形态：Node 宿主驱动
  Claude Code 常驻进程，Latent 走 HTTP；判据是当时五个业务工具握手成功，真实主聊天主动调用
  `latent_search` 并同时命中两段目标原文。采集条件为 VPS 生产环境、
  Latent `656a044`、Voyage `voyage-3.5`、182 个 Markdown／869 个切块。另有百来行参考宿主
  （`src/reference_host.py`）上的 DeepSeek／GLM 独立会话实测，见《注入契约》坑④。
  ⚠ 两份证据都不能替你的前端背书：自己拼请求时，注入契约仍要逐条自验
- **一台电脑不是必需的——但这条只对 Claude Code 成立**：纯手机走它的云端线程已实测
  全流程走通（见 §3b，有前提先看完）。**Codex 那边手机能聊，但本地那台机器要开着**，同节末尾单说。
  ⚠ **"只对 Claude Code 成立"说的是「整条路都有维护者实测」，别读成「没有电脑就只剩这一条」**：
  Android 上 Operit 按本机 stdio 拉起那条**同样不要电脑、也不要服务器**（见 §3c 部署形态一）；想在 claude.ai 聊天窗口里用则要一台公网服务器
  （§3c 部署形态二）。三条各自的代价不一样，**按你要哪个界面挑，不是按有没有电脑判死**。
  ⚠ 无论走哪条，**初始化都得在一个能跑 Python 的环境里完成**（本地或云端会话都行）。
- 你和 AI 的历史对话导出（没有也行，零材料会只出协议底座，见第 2 节）

⚠ **产出目录准备进 Git 仓库时，别把它建在本项目的 clone 里。** 本仓库的
`.gitignore` 特意忽略了 `CLAUDE.md`／`AGENTS.md`／`persona.md`／`memory/`／
`mcp-config.json`／根目录的 `注入契约.md`／`*.bak`，是为了防止私人记忆误提交进
公开仓库。但如果你照着这个 clone 直接 push，**记忆库也会被静默排除**：不报错、push
显示成功，下个会话却什么都读不到。需要 push 的云端路线请单独建自己的私有仓库放产出
目录（`src/` 可以复制过去），或者明确删掉那些忽略规则；只在本机使用、不靠 Git 同步的
桌面路线不受这个问题影响。

## 已有成熟人格，只想接记忆服务？

这是现有 `--persona` 入口的另一种**用户选择**，不是系统替你判断哪条更高级：

- 想把原人格作为最高权重来源，仍让工具拆块、归入十二节并逐节确认：走下面七步编译；
- 不想重排自己长期维护的文件，只想接记忆检索和写回：显式选择
  `use_original_as_is`，走下面三步。

在 `src/` 目录下执行：

```bash
# 1. 选择原人格直接使用：正文不拆块、不重排；出货副本末尾会追加 Latent 记忆协议
python memory_init.py --out <产出目录> --persona <现有人格文件> --step inspect --existing-persona-choice use_original_as_is --json

# 2. 三条检索路线仍要你自己选；这里用不装依赖、语料不出本机的默认档举例
python memory_init.py --out <产出目录> --step route --route zero-dep

# 3. 按客户端出货；时区填记忆所有者本人所在的 IANA 时区
python memory_init.py --out <产出目录> --step ship --client claude-code --timezone <你的时区>
# Grok Build 改用这一条，输出到 <产出目录>/.grok/agents/companion.md
python memory_init.py --out <产出目录> --step ship --client grok --timezone <你的时区>

# 出货后用配置实际指向的语料目录体检；没另给 --corpus 时就是 <产出目录>/memory
python mcp_server.py --doctor --corpus <语料目录> --timezone <你的时区>
```

**这条路是你主动跳过 `extract`、`choose-sections`、`preview`，跳过不等于通过了三项编译
检查。** 原人格正文不会被解析后润色或重排；输出文件也不是输入文件的字节副本——末尾会多一段
带 `LATENT_MEMORY_PROTOCOL` 起止标记的受管协议。以后重跑只替换标记之间的内容。输入文件在
产出目录外时不改；输入与目标恰好同路径时，覆盖前先留 `.bak` 并把路径打到回执里。

⚠ **部署到另一个仓库、容器或目录时，复制整个 `src/`，不是挑几个“看起来核心”的
`.py`。** `mcp_server.py`、`memory_retrieval.py`、切块、会话与时区模块之间有交叉依赖；当前
不是安装包，只加一个 `__init__.py` 也不会替你补齐缺文件。

⚠ **云端容器里的写回必须持久化。** `latent_append` 只写进当前磁盘；临时容器回收就没了。
把新增记忆提交后用 `git push origin HEAD` 推当前分支，再合回默认分支。写死 `main` 可能推到
一条没改过的本地分支并显示成功；只 push 不合回默认分支，下次 clone 同样读不到。

## 0. 导出历史对话（有历史记录才需要）

- **Claude**：设置 → 隐私 → 导出数据，邮件里下载 zip。
  **时间范围一定选"全部"，不要选"最近 30 天"**——选 30 天会把窗口外的对话
  全部框空，导出来近乎是空的（踩过）。

⚠ **别用旧的导出包——这个坑比上面那个隐蔽得多**（也踩过）：导出是**快照**，
你上次导出之后发生的所有对话都不在里面。旧包的数据完全真实、条数看着也漂亮，
它只是**停在了过去某一天**——建出来的人格文件会认得那时候的你，不认得现在的你，
而且"当下状态"会停在那一天。

所以**导入完先看一眼时间范围**，这一步别省：

```
python memory_import.py --stats <你的导出文件，或整个语料目录>
```

**目录也吃**（递归），语料是解压出来一堆文件时不用先挑。目录里认不出格式的文件
（图片、pdf、别家的 json）会被逐个报出来、不计进条数，跑完退出码非 0——
**那不是崩了**，是告诉你上面那个数没盖住整个目录。目录里的 README、随手记那种
散文读得进去但解析不出条目，也会被点名并从文件数里剔除，**这类只报不红**。

它会报条数和时间范围，并把**最新的那个日期**单独摆出来。**盯住那个日期**，问自己一句："我跟 TA 最近一次
聊天，真的是这天吗？"对不上就重新导一份。真实案例：一份看着很健康的导出
（两千多条、全部带时间戳），时间范围却停在五周前——因为那是几周前导的旧文件。

⚠ **正文和文件名里都没日期的文件**（README 那种），时间戳只能退回"文件修改时间"。
这种**不参与上面那个日期**，会另起一行告诉你排除了几条——拷一遍目录它就变成"刚刚"，
算进去等于**把旧快照伪装成新语料**。⚠ 要是它打的是"**这道体检在这份语料上无效**"，
说明你这份语料压根判断不了新旧，**别当成查过了**：把日期写进文件名
（`window_04_2026-06-17.md` 这种）或标题行再跑。
- **ChatGPT**：设置 → 数据控制 → 导出，拿到 `conversations.json`。
  （此格式按公开结构编写、没跟真实导出核对过，先跑
  `python memory_import.py --stats <文件>` 看条数/时间范围对不对，再往下走。）
- 微信没有官方导出，第三方工具格式不一，暂不保证。

## 1. 初始化：来源编译七步走

在 `src/` 目录下执行。产出目录建议新建一个**专属文件夹**（比如 `D:/companion/`），
后面客户端也从这个文件夹起会话——Claude Code 的 `CLAUDE.md`、Codex 的
`AGENTS.md` 与 Grok Build 的 `.grok/agents/companion.md` 都按目录生效，放进工作项目里
会跟工作用的配置打架；generic 档的
`persona.md` 不会被宿主自动读取，要按《注入契约》接入。

```bash
# 第 1 步：检查来源。三种入口三选一
python memory_init.py --out <产出目录> --persona <现有人格文件> --corpus <导出文件或目录> --step inspect --json
python memory_init.py --out <产出目录> --corpus <导出文件或目录> --step inspect --json
python memory_init.py --out <产出目录> --step inspect --json

# 改过人格文件后重跑 inspect 会摊开「上次 N 块 → 这次 M 块」的差异表
# （这个数只数正文块，不含 markdown 标题行——标题由十二节骨架统一渲染）；
# 某节这次一块都没有＝ blocking（多半是删了那节的标题行，正文顺延塌进了上一节）。
# 确实是有意删的，才加这个开关降为 warning——它不会改你的任何文件。
python memory_init.py --out <产出目录> --persona <现有人格文件> --step inspect --json --accept-persona-drift

# 第 2 步：导出零密钥提取任务包；把 persona-extraction/ 三份文件交给你当前的模型
#         （输入清单里带 anchors 锚表：模型挑锚号即可，不用自己数字符偏移）
python memory_init.py --out <产出目录> --step extract --json

# 模型返回严格 JSON 后读回；来源和逐字证据不合格会在这里拦住
python memory_init.py --out <产出目录> --step extract --candidates <候选结果.json> --json

# ⚠ 修过候选结果要重传时，--candidates 会用新文件替换旧语料候选；随后必须从
# choose-sections 重新选择十二节版本，旧选择不会沿用，避免把已替换候选的版本误带进出货。

# ⚠ 这一步的三份文件是**自足**的：`candidate_kind` 的合法取值、每种各自还要给哪些
# 字段、来源交代表那两个键名（candidate_item_ids / no_supported_candidate），
# 提示词和 schema 里都写清了——你的模型不需要（也读不到）本项目源码。
# 读回时看两类回执，别只看有没有 blocking：
#   · blocking_issues：过不去的，逐条按错误码改。键名写错会被指名说是键名问题，
#     ⚠ 我们不猜同义词（填成 item_ids 不会被自动认成 candidate_item_ids）。
#   · warnings 里的 CANDIDATE_KIND_UNCHECKED：那条候选的 kind 填了枚举外的值，
#     **它没有被任何结构检查**——不报错不等于验过了，把 kind 改成表里的值再跑一次。

# 第 3 步：取得十二节完整版本选择题
python memory_init.py --out <产出目录> --step choose-sections --json

# 若返回 original_mapping_questions，先把无法归节的原文整块选到一个主节
python memory_init.py --out <产出目录> --step choose-sections --original-section-decisions-json <原文块归节选择.json> --json

# 原人格里留着没填完的模板残句（“……去语料里找：……”）会被 TASK_DIRECTIVE_REMAINS 拦下；
# 出口在这一步：那一节会多一个「删除该块」的 section_version（带 diff），选它就能出货，
# 不用回去手改输入人格文件（手改正是上面塌节的雷区）。
#
# ⚠ 旧版工具生成的人格文件里常留着「它」（比如 `**它该记住你哪些方面**：…`）——
# 人格文件里的 AI 不写成「它」。出货时会打一条 BANNED_WORD_REMAINS ⚠ 并**指到行**，
# 那一节同样多一个带 diff 的「删除该块」版本。**这条不拦你出货**：你原文里若是
# 正当用法（指某个东西），留着就行——我们不替你改原文。

# ⚠ 每一节除了"照单全收"之外，只要那节的材料**全是语料候选**，还会多一个
# `<节>:leave_empty`「本节留空」的选项——**这一节不写进人格文件**。它存在的理由是：
# 校验器只验 evidence 逐字对得上原文，**逐字对得上的废话也是逐字对得上**，
# "真有东西"和"为了交代硬凑"在自动闸那里长得一模一样，这一步是唯一分得出来的场合。
# 选项里会写清留空会丢掉哪些来源；⚠ 那些来源**仍然算「已交代」**，不必回去改
# 候选结果.json，语料本身也一个字不会动。
# ⚠ 有你原人格块的节、以及有协议默认值的节**不给这个选项**：前者要逐块走
# 「删除该块」（带 diff，看得见删了什么），后者是骨架、留空会直接把出货拦死。

# 把每节选中的 section_version ID（字段名 `version_id`）交回；没材料的节选 leave_empty
# ⚠ 版本号随重跑变：交回一份过期的选择会被 SECTION_VERSION_STALE 拦下并点名，
# 重跑一次 choose-sections 看当前号再选（不拦的话那一节会整节从出货文件里消失，且不报错）
python memory_init.py --out <产出目录> --step choose-sections --section-decisions-json <十二节选择.json> --json

# 第 4 步：一次性看完整人格预览
python memory_init.py --out <产出目录> --step preview --json

# 第 5 步：选检索路线（三条路 + 各自代价会打出来，选回默认也算选过）
python memory_init.py --out <产出目录> --step route --json
python memory_init.py --out <产出目录> --step route --route zero-dep

# 第 6 步：按客户端四选一，出货四件套
python memory_init.py --out <产出目录> --step ship --client claude-code
python memory_init.py --out <产出目录> --step ship --client codex
python memory_init.py --out <产出目录> --step ship --client grok
python memory_init.py --out <产出目录> --step ship --client generic
```

`--client grok` 产出项目级主会话 agent：`.grok/agents/companion.md`。在 Grok Build 的
`/agents` 中选择 `companion`，或从产出目录运行 `grok --agent companion`。这里采用
`agents/*.md`，不采用只供子 agent 行为叠层的 `.grok/personas/*.toml`。文件格式已按 xAI
Grok Build 官方指南核对；本项目尚未在真实 Grok CLI 中启动验证，不把格式核对写成真机跑通。

`--persona` 和 `--corpus` 不是同一个入口。前者是最高权重的完整人格，默认只逐字保留
或移动；后者是用来补缺的语料。即使人格文件放在语料目录中，程序也会把它从 corpus
清单排除，不能让它作为普通记忆被切碎。

用户全程只选择已有的完整节版本。候选必须能回指来源；原人格 rewrite/delete 与硬边界
冲突会把 diff 和理由放进对应节题目，没确认就不能出货。完整预览不再增加一次全局批准。

**第 5 步为什么是一个必须过的步骤、不是可选升级**：三条路线里有一条（云端）
会把**查询和被检索的内容发到第三方服务商**。语料去哪儿不是快一点慢一点的取舍，
是不可逆的信任问题——所以这一步不给静默默认，得你自己选一次。三条路的完整对照
见下面第 5 节；不想折腾就选 `zero-dep`，那是默认档，什么都不用装。

**⚠ 往同一个产出目录出第二遍货会被拦一次**：`memory/timeline/`
里已有的窗口如果会被这次改样，出货停下来并报 `CORPUS_TIMELINE_OVERWRITE`。
**不是出错**——你后来靠记忆写回（`latent_append`）攒下的窗口就长在那些文件里，
盖掉就取不回来了：人格文件能重新生成，记忆不能。两条出口，挑一条重跑第 6 步：
`--backup-corpus`（先把整个 `timeline` 备份成 `timeline.bak` 再写，**只加不减**，
已有备份就顺号成 `timeline.bak2`；拿不准就用这条）、`--accept-corpus-overwrite`
（我知道会覆盖，就这么办）。想留着现在这份记忆库不动，**换一个 `--out` 目录**即可，
没有专门的开关做这件事。⚠ 第一次出货、以及同一份语料原样重跑都不会被拦——判据是
「内容会不会变」，不是「目录空不空」。

⚠ **这段护栏只在「我们替你把语料写进产出目录」那条路上生效，上面七步走够不着它**：
护栏挂在写语料那一步（`write_corpus`）上，
而**七步走的第 6 步根本不写 `memory/timeline/`**——它只把你 `--corpus` 指过去的目录
读一遍算覆盖区间。所以走七步走的人**不会看到 `CORPUS_TIMELINE_OVERWRITE`**，
`--backup-corpus` 与 `--accept-corpus-overwrite` 这两个开关在这条路上**加了也不起作用**。
⚠ **这不代表你的记忆更安全或更不安全**——七步走本来就不动那些文件。
会走到护栏的是另一条：出货时用 `--import <导出文件>` 让我们替你建库那种。
如果 inspect 时给过外部 `--corpus`，ship 又显式给 `--import`，以本次导入为准：窗口写进
`<产出目录>/memory/timeline/`，生成的 `mcp-config.json --corpus` 也改指
`<产出目录>/memory`；原外部目录保持只读，不会出现“导入成功但服务仍读旧目录”。

出货后产出目录里有四样：

| 文件 | 是什么 |
|---|---|
| 人格文件：Claude Code 用 `CLAUDE.md`，Codex 用 `AGENTS.md`，Grok Build 用 `.grok/agents/companion.md`，通用／自建前端用 `persona.md` | 核心人格文件；是否自动进入常驻上下文取决于客户端，见 §3c 与 §4b |
| `memory/` | 产出包拥有的记忆目录。七步走时叙事层仍在你 `--corpus` 指的外部目录，这里只创建独立 `index/`；用 `--import <导出文件>` 由我们建库时，`timeline/` 也落在这里 |
| `mcp-config.json` | **配置样板，不是生效配置**——见下方说明 |
| `引导句.txt` | 一行指针，**只有闭源前端 App 用得上**（贴进它的设置字段），宿主客户端不用管它——见 §3c |

`memory/index/` 每次出货都会创建，里面的 `README.txt` 是说明，**不是摘要**。
生成的配置用 `--index-dir` 把它作为第二个检索根；`latent_append` 必须交付正文和当下状态，
推荐同批交付 `indexEvidence` 原文证据。证据通过时同时写入 timeline 与 index；不通过时
正文仍写入 timeline，回执给出 `recordId` 与 `indexStatus=pending`，之后可按该标识补索引。
doctor 始终只读；服务写回时 index 根可写。你的外部语料目录仍然只读，出货不会
替你建 `corpus/index/`；已有的 `corpus/index/` 继续兼容，不迁移、不复制。

### 手工调用 `latent_append` 的完整参数

模型或第三方宿主不再自行拼日期、粗体、换行和“两行四段”。只需给正文、当下状态，以及从
二者逐字摘出的证据片段；服务端负责统一生成索引：

```json
{
  "text": "下次想去看企鹅漫步。最好挑个凉快的早上。",
  "current_state": "新约定，档期还没定",
  "unresolvedOps": [
    {"action": "open", "summary": "企鹅漫步的档期还没定"}
  ],
  "indexEvidence": [
    {"type": "event", "quote": "下次想去看企鹅漫步"},
    {"type": "reason", "quote": "最好挑个凉快的早上"},
    {"type": "state", "quote": "新约定，档期还没定"}
  ]
}
```

想先确认参数、绝不写盘时，在同一份参数里加 `"mode":"preflight"`。预检复用实际写入的
正文、原文证据、旧摘要和未解决项校验，并返回预计窗口、文件、`recordId`、`indexStatus` 与
`preflightStatus=ready`；通过后删除 `mode`（或改成 `write`）再调用。写入时会重新校验，
预检结果不是跳过校验的确认令牌。工具整体仍有写入能力，因此 annotations 继续标为非只读。

参数错误会在同一条工具回执中给同类最小对照，例如：

```text
索引证据无法映射回原文……
写错：{"indexEvidence":[{"type":"event","quote":"她计划下周复查"}]}
写对：{"indexEvidence":[{"type":"event","quote":"她说下周要去复查"}]}
```

预检不带 `indexEvidence` 也可以通过，但会明确返回 `indexStatus=pending`；这表示正文参数合法、
真正写入后仍需按回执里的 `recordId` 补索引，不等于索引已经就绪。

`unresolvedOps` 在兼容模式下可省略：旧客户端的正文仍会保存，但回执会明确给
`unresolvedStatus=not_reviewed`。新调用应显式给 open／update／close，或无变化时传
`[{"action":"none"}]`。要让缺字段在写盘前直接失败，服务端启动参数加
`--require-unresolved-review`；这只卡字段缺失，清单文件损坏仍不会吞掉正文。

`type` 只取 `event`／`feeling`／`reason`／`state`／`context`。服务端容忍空白、全半角和
中英文引号／标点形态差异，但不接受同义改写；最终写进 index 的是服务端重新定位出的原文。
证据失败时正文仍保存，回执形如 `recordId=…，indexStatus=pending`。此后补索引只调用：

```json
{
  "recordId": "此前回执里的16位标识",
  "indexEvidence": [
    {"type": "event", "quote": "下次想去看企鹅漫步"},
    {"type": "state", "quote": "新约定，档期还没定"}
  ]
}
```

补索引时不要再传 `text` 或 `current_state`，否则会被明确拒绝；因此不会为了修索引重复写正文。
补索引同样可先加 `"mode":"preflight"`，确认 recordId 与证据有效且尚未生成索引；预检不会
创建索引文件，已经有索引时会明确返回“无需重复补索引”。

### 精准清理一条误写：先预览，再确认

`latent_cleanup` 只接受 `latent_append` 回执里的 16 位 `recordId`，不按相似文字、标题或短引文
猜目标。先调用：

```json
{"action": "preview", "recordId": "此前回执里的16位标识"}
```

预览纯读，会返回正文片段、关联索引数和绑定当前文件快照的 `confirmation`。确认确实是要清理的
误写后，再逐字交回令牌并说明原因：

```json
{
  "action": "delete",
  "recordId": "此前回执里的16位标识",
  "confirmation": "preview 返回的完整令牌",
  "reason": "把星期二误写成星期三"
}
```

两次调用之间正文、关联索引或受影响 sidecar 有变化，旧令牌会失效，必须重新预览。未解决清单
仍引用该 `recordId` 时也会拒绝，并点出须先 update／close 的事项 ID。成功前，服务端会把本次
涉及的原始文件保存到 `<corpus>/.cleanup-trash/`：副本用 `.bak`，不会被当成语料重新加载；
`manifest.json` 记录原路径、SHA-256、原因和 UTC 时间。它只清 Latent 自己写下的单条记录，
不提供批量删除，也不替代普通导入语料的 `latent_correct`。

#### 旧 `indexSummaries` 的逐字校验规则

新调用优先使用上面的 `indexEvidence`；旧客户端仍可传 `indexSummaries`。兼容校验器按下面的
规则逐字判断，不会替调用方猜意思：

1. `summary` 必须完整匹配
   `^\*\*YYYY.MM.DD\*\*：(A)。\n(B)。\*\*当下：(C)。\*\*$`。报错里的第 1／2／3 段
   分别指 A／B／C，不包含日期段。
2. 证据底稿是 `evidence_base = text + "\n" + current_state`；`current_state` 与正文一样
   参与证据校验。
3. 每个 `evidenceTerms` 证据词必须**同时**是 `summary` 的子串，也是 `text` 或
   `current_state` 的子串。只在正文里有、却没写进摘要，仍然是越界词；只在摘要里有也一样。
4. 比较就是纯子串比较：标点参与，不分词、不认近义词、不忽略虚词，也不做归一化。

此外，A／B／C 每段都至少要含一个合格证据词。格式错误会直接指出不匹配的是 A、B 还是 C；
越界错误会指出该词缺在 `summary`，还是缺在 `text/current_state`。

#### 已有语料但索引层是 0 块

绕过 `latent_append`，直接把 Markdown 正文提交进语料目录时，timeline 会有内容，但不会自动
生成索引层。发现方法是用实际配置参数运行 `--doctor`，看“建库”一行：如果叙事层有块、
索引层显示 `0`，正文虽然已进库，检索质量会低一档。

对这种没有 `recordId` 的旧语料，不要重新调用 `latent_append` 把正文写一遍。应在实际配置的
`--index-dir` 下，为已有语料逐份补唯一命名的 `.md` 索引文件；旧部署没配该参数时才放进
`<corpus>/index/`。每份只写从对应正文逐字摘出的高密度证据，不补正文没有的推断，例如：

```markdown
**2026.08.29** · 原文证据索引
事件：拆开发现咖啡机保险丝熔断；换好保险丝后恢复加热
状态：咖啡机已经修好
```

补完再次运行 `--doctor`：判据是索引层块数从 0 变为实际补入数，且拿正文中的一句原话做
检索自查能命中。`README.txt` 只是说明文件，不算索引块；不要为了让数字变绿而复制正文、
伪造摘要或重新初始化现有语料。

### `mcp-config.json` 是样板，放着不动不会生效

**没有任何客户端会自动读产出目录里的这个文件。** 它是给你抄进自己客户端配置的
样板，抄完它的使命就结束了：

- **Claude Code**：走下面第 3 步那条 `claude mcp add`（或者在项目根目录写
  `.mcp.json`，见 3b）。配置落在客户端自己的地方，不在产出目录。
- **其它客户端**：把里面的 `mcpServers` 那段抄进该客户端的 MCP 配置文件。

**文件里第一行 `"_说明"` 就写着这件事**——JSON 没有注释，
所以那是一个真键；你抄的时候抄 `mcpServers` 那一段就行，不用带上它。

所以**改了 `mcp-config.json` 不会有任何效果**——要改就改客户端那边真正生效的
那份（重跑一次 `claude mcp add`，或直接编辑 `.mcp.json`）。产出目录里留着这份
样板只是方便你复制，它不参与运行。

### 换了台机器怎么办（配置跟着机器走，这条真有人栽过）

先认症状：换了机器/容器之后，**AI 突然"好像不太记得事"，而且没有任何报错**。
这多半不是库坏了——是 MCP server 压根没起来。server 起不来不会有一句话告诉你，
会话照开、模型照回话，只是它没有那六个记忆工具。这个症状跟"语料没进去""模型
不主动查"长得一模一样，所以先分辨：`claude mcp list` 看 memory 服务连着没有，
或者按 §4 开新会话验一次。

**原因**：配置里的路径是**这台机器的绝对路径**（这是有意的：相对路径在"客户端
从哪个目录起进程"上是赌博，我们不赌）。代价就是它跟着机器走——换机器、换容器、
换用户名，同一份配置就是一句不报到你脸上的 file not found。真实案例：一位用户的
配置跟着仓库进了云端容器，`cwd` 指着旧机器的家目录，那台容器上根本没有那个路径。

**修法**：在新机器上重跑一次出货（答案和确认结果都在 `init_state.json` 里，
原样重放、不用重答），再把新的 `mcp-config.json` 抄进客户端：

```
python memory_init.py --out <产出目录> --step ship --client <你的档>
```

**例外：Claude Code + 整套进仓库（§3b 那种形态）不用重跑。** 出货时如果四个路径
（`src/`、叙事语料、`memory/index/`、`threads.jsonl`）都在产出目录下，Claude Code 档产出的配置
自动用 `${CLAUDE_PROJECT_DIR:-.}` 占位符——它随仓库走，克隆到哪台机器都指得对。
三条边界：

- **这个占位符只有 Claude Code 认**。Codex、Kelivo/Operit、自建前端（包括
  `reference_host.py`）拿到它就是 file not found——所以只有 Claude Code 档会产
  这种写法，其它档拿到的永远是绝对路径。别把可搬运那份抄给别的客户端。
- **前提是产出目录就是你在 Claude Code 里打开的那个目录**（§3b 那种整套进仓库的
  形态）。记忆包放在别的项目子目录里的（比如包在 `myapp/memory-bundle/`、你在
  `myapp/` 开 Claude Code），这份配置指不对——它会去找 `myapp/src/mcp_server.py`，
  而且同样是那种不报错的失败。**这种摆法请用绝对路径档**（出货时不带
  `--client claude-code`，或干脆把包放成项目根）。
- **它到底靠什么指对，值得知道**：这个变量是设在**服务端进程**的环境里、不在
  Claude Code 自己的环境里，`.mcp.json` 展开的时候读不到它——所以**实际展开出来
  的永远是默认值那一支（`./…`）**。它能指对，是因为 Claude Code 起 server 时的
  工作目录就是项目根，**这是实测观测到的行为，不是文档承诺的**。换 Claude Code
  版本后如果这一节里说的形态突然不灵了，先怀疑这一条，别去查变量有没有注入。
- 成色：**本机已实测**（新会话真起 server：当时六个工具在、检索命中、
  写回当场可查）；**跨机器（云端容器）那一步未实测**——理论上正是为它设计的，
  谁在容器里跑通了欢迎回来说一声，这里照实改。

### 时区那一行：`--timezone`（装在服务器上的人一定要看）

**自然日 ＝ 你配的那个时区的 00:00～23:59**，没有别的规则、没有凌晨偏移。写回落进
哪个窗口文件、记录标题上的日期、检索片段的 `[日期]` 标签，全按这一个口径算。

**不配会怎样**：用默认值 **`Asia/Shanghai`（东八区）**——**你在东八区就正好，不在的话
现在写下的日期就是错的**，而且不会报任何错。⚠ **服务端不会去探测它自己那台机器的
时区**——这是有意的：那样一来同一份配置换台机器就换个答案，错得更隐蔽。
现在的错法是固定的、写在配置里的，你能一眼看出对不对。真实事故：人在东八区，
服务器是 UTC 的 VPS，当地凌晨 02:03 记下的五条记忆**全被记成前一天**，而工具每一次
都返回成功。这不是显示问题：那个日期同时进文件名、记录标题、检索标签，重启之后
还会变成"哪条更新"的排序依据，而召回块的规矩是"同类相关的记忆以日期最近的一条
为当下状态"——日期错一天，AI 对"你现在是什么状态"的判断就跟着错。

**怎么配**：在 `mcp-config.json` 的 `args` 里加一行（换成你的 IANA 时区）：

```json
"--timezone", "Asia/Shanghai"
```

出货时也可以直接带上：`python memory_init.py --out <产出目录> --step ship
--timezone Europe/Berlin`。**不给的话出货配置里落的是默认值 `Asia/Shanghai`**，
并在配置说明里写明"这是默认值、不对就改这一行"。**我们不会拿探到的宿主时区顶替它**
——能探到的只是"跑初始化那台机器的时区"，那不是你的时区（在 VPS 上探出来正好是
UTC，替你填上等于把这个缺陷盖成绿的）。也可以走环境变量 `MEMORY_TIMEZONE`。

- **配错名字会当场报错、不起服务**（不会偷偷退回 UTC）。
- ⚠ **Windows 上要先装时区数据（这是前置条件，不是出问题再看的排障条目）**：
  Windows 裸装的 Python **不带 IANA 时区数据库**，`Asia/Shanghai` 这类 IANA 名认不出来。
  配 IANA 名之前先 `pip install tzdata`；不想装就退一步写固定偏移
  `--timezone UTC+08:00`——⚠ 固定偏移不懂夏令时，只有常年不换偏移的地区（中国就是）才等价。
  ⚠ **为什么写成前置条件**：这一步失败时服务端确实会打出一段带 `pip install tzdata`
  的人话，但**那段话走 stderr，MCP 客户端按 stdio 拉起时会把它丢掉**——
  客户端上只显示「连不上」，你看不到任何提示（已实测）。
  所以**别指望报错来提醒你**，装之前就装上。
- **没配的话 `--doctor` 仍然报 ⚠**（并打出它实际在用的那个默认时区），配了才报  加名字。
  ⚠ 这一格**故意没有因为"有默认值了"就降成 **：默认值对东八区以外的人就是错的，
  报成  等于对着可能错的日期发合格证。

### 语料目录的三条约定（外层名字随便，里面两条不随便）

1. **最外层目录叫什么都行。** 服务端认的是 `--corpus` 传进去的那个路径，不是
   `memory/` 这个名字——手动建成 `corpus/`、`我的记忆/` 都一样读得到。
   看不到 `memory/` 不等于没跑通，看 `--corpus` 指向哪儿才作数。
2. **`index/` 是硬约定。** 判定只看一层：**父目录名叫 `index` 的算索引层，其余
   一律当叙事层**。索引层是每个会话一条高密度摘要、专门喂检索，命中之后下游才
   知道"这是摘要、正文在叙事层那边"。把摘要放在 `LTM/`、`profile/` 这类名字下，
   它们照样进库、照样能被检索到，**但分层信息就没了**——命中一段摘要时，
   没有东西告诉模型"完整的那份在别处"。
   `index/` 可以是 `--corpus` 里面的旧式子目录，也可以由 `--index-dir` 指向产出包里的
   独立目录；两者都读，写回、权重和缓存始终只落 `--corpus`。
3. **文件名带日期很重要。** 时间戳优先取文件名里的日期（`window_04_2026-06-17.md`
   这种）；文件名没有时还会去正文开头几行和标题行找日期、再试同窗口号的邻层文件，
   **都找不到才退到文件修改时间（mtime）**。而 mtime 在这里不是"不太准"，是
   **全错且整齐地错**：复制一遍目录、重新 clone 一次仓库，所有文件的 mtime 会被
   刷成同一时刻，于是一整批记忆拿到同一个假时间戳。换窗开场召回正是按时间新鲜度
   排序的，这一错就整个乱套。

   这条是踩过的坑不是洁癖。**上面那几级解析能救回来的，是「日期写在正文或标题行里」
   的语料**（我们自己一份文件名不带日期的真实语料，靠这几级把落 mtime 的块从 95.6%
   压到 **0%**）——**文件名不带日期、正文里也没有的话，它们一样救不了你**。

## 1b. 已经建过一份，怎么升级到新版

`git pull` 拿到新代码之后：

1. **记忆库不用动**——`memory/` 里那些 md 一个字都不用改。
2. 先让新版识别产出目录里已有的人格文件：

   ```bash
   python memory_init.py --out <产出目录> --step inspect --json
   ```

   程序只给两项：把当前文件作为最高权重原人格，或继续旧 v1 流程。不会静默选择。
   要进入新版来源编译器，运行：

   ```bash
   python memory_init.py --out <产出目录> --step inspect --json --existing-persona-choice treat_current_as_original
   ```

   然后按 §1 从 `extract` 继续。旧人格里的手改段落会成为带精确字符区间的原文块，
   rewrite/delete 仍需在对应节看 diff 后选择。
3. **`mcp-config.json` 重新抄进客户端**：启动参数跟检索路线绑定，
   选了本地模型或云端就跟原来不一样了；那份文件自己不会生效（见上一节）。
4. 你当初要是把 `src/` 复制进了产出目录，记得也换成新的。

v1 `init_state.json` 不会被静默重解释成 v2；选择 `continue_legacy` 后仍可按旧命令续跑。

## 2. 没有历史记录？

一样能用：

- 有丰富语料但没有人格文件：当前模型从真实来源提取具体身份、里程碑、双向称呼和
  完整对话片段，用户只选择节版本。
- 只有稀薄语料：能支持多少就写多少，找不到的节选 `leave_empty`。
- 完全没有材料：不加 `--persona`、不加 `--corpus`，只生成检索、会话、拒绝权和证据
  边界等协议底座；不会虚构关系状态、边界或最终约定。

人格可以短，但短是因为材料确实少，不是因为把已有身份、边界和声音压没了。

## 3. 接入 Claude Code

> 不用 Claude Code、想在**聊天窗口**里用？先看 [§3c](#3c-哪些客户端能接哪些不能以及聊天窗口那格的现状)——**默认档连不上聊天窗口是结构原因，多半有更省事的走法**（另有一条公网通路，已实测接通，也在那节）。

```
claude mcp add memory --scope user "--" python <src绝对路径>/mcp_server.py --corpus <叙事语料目录> --index-dir <产出目录>/memory/index --threads <产出目录>/threads.jsonl
```

踩过的坑：

- **PowerShell 会吞掉裸的 `--`**，要像上面那样带引号写成 `"--"`。
- 不加 `--scope user` 时配置只对当前目录生效，换目录起会话就找不到了。
- 路径用正斜杠 `/`，Windows 一样认，省去转义麻烦。

然后**从产出目录起会话**（人格文件在那儿才会被读到）。

## 3b. 没有电脑？云端线程也能接（**已实测跑通**，但有前提）

先分清两件事：**官方 App 里的普通聊天窗口不能拉起你电脑上的本地 stdio 服务**；
要在普通聊天窗口里用，必须另有一个公网可达的远程 MCP。VPS＋Connector 这条路线
已经在 claude.ai 的自定义 Connector 上接通，见 §3c「claude.ai Connector 那一格」。但**官方 App 里的
云端线程入口**（Claude Code 的云端会话）不一样——那是一个完整的 Linux 容器，
Python 有、能起进程、能拉 GitHub 仓库，所以整套东西可以跑在里面，
**全程一台手机，不碰电脑**。

做法：把产出目录（人格文件 + `memory/` + `src/`）放进一个 **GitHub 私有仓库**，
在**仓库根目录**放一份 `.mcp.json` 声明记忆服务，云端会话起来会自动读它。
来源编译初始化也可以直接在云端容器里跑（十二节选择与预览照走，所有接口都可非交互调用）。

`.mcp.json` 长这样（进程型，服务跑在容器里）：

```json
{
  "mcpServers": {
    "memory": {
      "command": "python",
      "args": ["src/mcp_server.py", "--corpus", "memory", "--threads", "threads.jsonl"]
    }
  }
}
```

⚠ `command` 那一行按**你那个容器里真有的命令**填：不少环境只装了 `python3`，
没有叫 `python` 的命令，而这种情况下客户端只会说"连不上"，不会指到这一行。
先在容器里 `which python` 确认一下。（出货目录里那份 `mcp-config.json` 不用管，
它现在会自己探这台机器上能跑的解释器。）

### 开场召回要稳：优先交给 `SessionStart` hook，不只靠模型自觉

⚠ **hook 不是自动召回的前提。** 主机制是人格文件里那句「提到过去先查库」——
没有 hook 的客户端（Operit／Kelivo／Grok 聊天端／自建前端等）**同样是自动的**，
只是依赖模型服从度；`SessionStart` hook 是 **Claude Code 独有**的加固，
把它变成强制执行。同样没有 hook 的 Claude 桌面 App 那格已实测
**模型 4/4 主动调用 `latent_session_start`**（采集条件见本文 §3c「客户端矩阵」那一行）。

`.mcp.json` 只负责**把工具挂上来**，不保证模型第一轮会调用。Latent 的 server
instructions 与人格文件虽然都要求“开场先调 `latent_session_start`”，但这仍是模型服从问题；
我们自己的跨模型记录早已见过开场约定比按需检索更不稳，2026.08.19 又收到一例 Claude Code
云端反馈：第一句先处理别的任务，聊到记忆库后才补调。

如果你的 Claude Code 环境允许项目级 hook，**建议把开场召回放到 Claude Code 的
`SessionStart` hook**：由 hook 请求 Latent，再把返回内容通过 stdout 或
`additionalContext` 注入开场上下文。这样由宿主生命周期执行，不再把“要不要调”留给模型。
Claude Code 官方文档确认 `SessionStart` 会在新建、恢复、`/clear` 与压缩后的会话启动时运行，
并把 hook 输出放到第一条用户提示之前。

这条目前是**官方机制核对＋一例外部方案反馈，我方没有同环境复现**。反馈方用的是自己的
curl 接法；不同部署可能还要走 MCP 握手或 HTTP 适配层，所以这里不提供一条假装通用的 curl
命令。实现时给 hook 设短超时、限制返回长度，失败要看得见但不要锁死整场会话；凭证和私人
记忆不要写进仓库或日志。`.mcp.json` 仍要保留，后续 `latent_search`、写回与更正仍走工具。
采集条件缺口是 hook 配置、HTTP 请求、模型型号、Claude Code 版本与改前／改后连续次数，
所以不要把这条建议转述成“已解决”或成功率数字。

如果你自己有服务器、想让记忆库常驻在那儿（容器每次重建也不影响），
可以改成 HTTP 型，指向你自己部署的那份服务：

```json
{
  "mcpServers": {
    "memory": {
      "type": "http",
      "url": "https://<你的域名>/mcp",
      "headers": { "Authorization": "Bearer ${你的TOKEN环境变量}" }
    }
  }
}
```

**三个前提，接受了再走这条路**：

1. **记忆库要托管在 GitHub**。桌面路线记忆只在你自己机器上，云端路线等于把它
   传到别人服务器上——**这两条在隐私上不等价**，别把它当成同一件事的两种敲法。
2. **容器是临时的，写回必须推回仓库**。`latent_append` 写进的是容器磁盘，
   会话一结束就没了。人格文件里要写明"聊完把新增记忆 commit + push 回仓库"，
   否则每次都从零开始，等于没有记忆。

   ⚠ **那句话里的分支名千万别写死成 `main`**（用户实测踩到，
   我们自己在容器里复现了）。云端会话经常不落在 `main` 上——它会切一条工作分支
   （`claude/…` 这种），而容器里**同时还有一条从远端拉下来的、干干净净的本地
   `main`**。这时候敲 `git push origin main`，git 推的是那条没动过的 `main`：

   ```
   $ git push origin main
   Everything up-to-date          ← 退出码 0
   ```

   **它成功了，而你今晚新长出来的记忆一个字都没上去**，还留在那条工作分支上，
   跟着容器一起被回收。这是这个项目最怕的那种失败：不报错、显示成功、
   下次会话什么都读不到——跟上面那条 `.gitignore` 静默排除是同一个病。

   写回那句话请照这个写，**推当前分支，不认分支名**：

   ```
   git add -A && git commit -m "记忆写回" && git push origin HEAD
   ```

   `HEAD` 就是“我现在在哪条分支就推哪条”，容器切到什么分支都对。推上去之后
   记忆在那条分支上，**回头合回主干**（或者直接把那条分支设成默认分支）。
   **不合回主干的话，下次会话照样读不到**——新会话 clone 到的是默认分支，
   那些记忆散在各条工作分支上，**跟没推是一个效果**，症状也一模一样。
   **改仓库的默认分支不能代替这一步**——只要会话另切了工作分支，写死分支名的
   那句话照样是空推。

3. **云端线程一般要付费档**，免费账号大概率没有这个入口。

**成色声明（分环节说，别整条打包）**：**不同环节的成色不一样，分开讲才诚实**：

**成色按"哪个客户端上验的"记**——跨客户端的结论不能互相借用（同一件事在
Claude Code 云端成立，不等于在 Codex 云端也成立，反过来同理）：

| 环节 | 在哪验的 | 成色 |
|---|---|---|
| 纯手机（不碰电脑）跑完整条路 | Claude Code 云端 | **已实测** |
| 云端会话会自动读仓库根目录的 `.mcp.json` | Claude Code 云端 | **已实测**——但我们验的是上面那个 **HTTP 型**配置 |
| 一句很短的人格文件就够让模型主动查记忆 | Claude Code 云端 | **已实测**，且这是这条路最关键的一环 |
| 本项目的 `mcp_server.py` 能在云端容器里跑起来、说 MCP 协议 | Claude Code 云端 | **已实测**（容器内起进程、握手成功） |
| 云端会话会不会**替你启动**上面那个**进程型**配置 | 两家都没验 | **没验过**——两头都验了，中间这一下没有 |

所以：想稳妥就用 HTTP 型（要有自己的服务器）；用进程型是**大概率能成但我们没跑过**，
成了或者卡住了都欢迎回来说一声，这张表会照实改。

**Codex 这一侧单独说**，因为验到的东西不一样：

| 环节 | 在哪验的 | 成色 |
|---|---|---|
| `--client codex` 整条链走通（初始化 → 确认 → 出 `AGENTS.md`） | 本地 Codex | **已实测**（产出的 `AGENTS.md` 逐行核对过） |
| 新会话第一句就主动查记忆（§4 那个验法） | 本地 Codex | **已实测**——非 Claude 客户端第一次验到，说明这套人格文件写法不只对一家模型有效 |
| 同样的路走 **Codex 云端**（不碰电脑） | 维护者实测 | **这条路不成立**——见下方说明 |

留一条给读者的提醒，是我们自己交的学费：**"这个客户端能跑"和"这个客户端的云端能跑"
是两件事**，中间差的正是"谁来启动记忆服务进程"这一步——恰好也是上面那张表里
唯一空着的一格。

**Codex 那条云端路不成立（维护者实测，结论比"没验过"确定）**：

- **不是"开不了"，是"当不了日常"**：Codex 的云端线程能聊，但**体验上立不住**
  ——它不是拿来当日常对话窗口的入口。所以"把仓库连上、每天在云端会话里聊"这条
  在 Claude Code 上成立的路子，在 Codex 上撑不起来。
- **能跑通的是初始化**：在"电脑不休眠 + 手机操作"这个前提下，初始化全流程走通了。

**日常聊天怎么办（这一条跟上面那条常被读混，分开说）**：

- **手机上照样能聊，但那台电脑必须开着。** 形态是**手机当客户端、本地那台机器
  跑实例**——不是云端容器在跑。这是这条路的**固有前提**，不是"配一下唤醒就能省掉"：
  电脑睡了这条路就断。所以 §3b 开头那句"全程一台手机、不碰电脑"**对 Codex 不成立**。
- **另一条是自己走一层中转**：把模型接到别的地方去聊——任何 API 中转（OpenRouter
  这类）、自建前端、别的支持 MCP 的客户端都行，**关键是那个"别的地方"要能读
  人格文件、能接记忆服务**。走自建前端的话，出货时用 `--client generic`，
  注入怎么拼见《注入契约》（§4b）。
  ⚠ **作为 Codex 手机日常路线，这条没测过**。维护者生产自建前端已经验过的是
  Claude Code 宿主＋Latent，不能把那一例的成色借给 Codex 手机路线。

## 3c. 哪些客户端能接、哪些不能（以及聊天窗口那格的现状）

被问过好几次的一个问题：**“MCP 在不同聊天端到底怎么接？”**先给结论表。

**表为什么是两列**：「能接」在有些客户端上只兑现一半——MCP 检索通了，
人格文件却不会被自动注入。检索能用 ≠ 人格能用，所以分开标。

| 客户端 | ① MCP 检索 | ② 人格注入 | 怎么接 |
|---|---|---|---|
| **Claude Code**（命令行 / IDE） |  已实测 |  自动读 `CLAUDE.md` | §3 |
| **Codex**（桌面 App） |  已实测 |  自动读 `AGENTS.md` | 出货时 `--client codex` |
| **Claude Code 云端线程**（手机也能开） |  已实测 |  已实测 | §3b |
| **Kelivo**（手机 App） |  能——server 原生 `--http` 直连（Kelivo 1.1.17 iOS）。⚠ 连不上先看绑定地址、不是协议：省略 HOST 只绑 `127.0.0.1`，手机连不到。⚠ 绑 `0.0.0.0` 是裸 HTTP 暴露公网、没有 TLS，推荐仍是绑回环 ＋ 反代管 TLS，见部署形态二。⚠ **2026.08.21 另一例并列，别互相顶替**：一位**安卓** Kelivo 用户报告**Kelivo 只支持 SSE、服务端是 Streamable HTTP，得自写代理桥接**（他自写了一个 `:8766` 的 SSE 桥）。⚠ **没给 Kelivo 版本号**。上面那条直连跑通的采集条件是 **Kelivo 1.1.17 iOS**——**可能是 iOS／安卓差异、可能是版本差异、也可能是他没试直连，三种都没排除**。**并列记，别拿任何一条去改另一条。** |  手工用文件导入进 system prompt，**容量不用担心**（实测 10M 字符仍不截断；真实人格文件低三个数量级） | 见下面「闭源前端这一类」 |
| **Operit**（手机 App） |  能，但**先按你的 Python 装在哪儿挑路**：①**同机回环 HTTP**（部署形态一之二，2026.08.21 外部实测跑通：proot 内起 `--http 127.0.0.1:8765`，Operit 走远程 MCP 连回环，当时五个业务工具＋写入＋检索全通）；②**本机 stdio 拉起**（部署形态一，2026.08.03 外部实测跑通，⚠ **那次同样是 proot，`command` 写的是 venv 里的 python**）。⚠ **2026.08.21 另一例在 proot 下没被拉起来**，但**别读成「proot 里不行」**——08.03 那次就是 proot。两次记录在案的差别是 `command` 写法（venv 里的 python vs 裸 `python3`）与配置结构，**都还没验过**（见部署形态一）。公网 `--http` 那条在 Operit 上仍无真机记录 | ❌ **不自动注入**，但**手工贴得下**：粘贴框（形态类似 system prompt）没有硬上限，⚠ 实用上限约 **20 万字符**——到这个量级保存会非常卡，再往上加会**让 App 强制重启**，所以别把语料也往里塞。改了人格文件要**手工重贴**（实测） | 同上 |
| **Claude 桌面 App** |  **已实测**（Windows／商店 MSIX 版）；当时五个业务工具全在；开场召回 `latent_session_start` **4/4 主动调**；**跨进程写回也通**（完全退出进程重开后仍查得到）。**按需检索**：人格文件里带着「风格片段不是记忆、提到过去先查库」那句 disclaimer 时，**模型会先调 `latent_search`**，查不到如实说没有（判据是**看工具真被调用**，不是看它答得好不好；MCP 走本地 stdio，disclaimer 手工贴进人格文件）。走 `use_original_as_is` 时工具会自动把这句随受管协议追加到出货副本；完全绕开本工具时才要手工补 | ⚠️ **手工贴进 profile**（**不是**自动读文件——它够不到本地文件，`引导句.txt` 那条指针路线在这里不成立）；**容量不是问题**（1.6 万字不截断＋前中后三段可读） | 见下面「桌面 App 那一格」 |
| **Grok 网页 Connector**（grok.com） | ⚠ **要先过 OAuth 发现层**：只填 MCP URL 时 grok.com 探测到 401 后弹 OAuth 凭据表（客户端 ID／授权端点／令牌端点／PKCE），**没有静态 API Key 选项，纯 Bearer 完不成「保存并连接」**。一位外部用户自建最小 OAuth shim（**用户侧扩展、非本项目功能**）后接通：当时五个业务工具可用、新 Project 窗口开场召回与写入跑通（**外部实测转录，本项目未复现**）。⚠ 成色**不外借**给下面两行，也不是 `grok-4.5` 服从度数据 | ⚠ 不自动读取本地人格文件，需在自定义指令／Project Instructions 里手工配置 | 部署形态二 ＋ 下面「grok.com 网页 Connector 那一格」 |
| **Grok Build**（CLI） | ⚠ **未实测**——`--client grok` 的产出格式（`.grok/agents/companion.md`）按 xAI 官方指南核对过，但**没有真实 Grok CLI 启动与 MCP 工具调用证据**；别拿上一行网页 Connector 的成色顶替 |  按目录自动读 `.grok/agents/companion.md`（从产出目录起会话） | §4a `--client grok` |
| **xAI API／Remote MCP Tools** | ⚠ **本项目无实测**。xAI 官方文档写明 SDK 与 Responses API 支持远程 MCP 工具，这只证明“产品具备入口”；没有任何一次本项目的接入或调用记录 | ⚠ 同样要自己把人格拼进 system prompt | 逐条查 xAI 官方文档 |
| **ChatGPT** | **State Ledger 部署已真机接通读链路**。Secure MCP Tunnel 从本机主动建立出站连接，不开放公网入站端口；ChatGPT Work 新窗口成功调用 `state_session_start` 并读取跨窗便签。⚠ 该服务使用独立 `state_*` 工具，不能当作本项目 `latent_*` 七工具的调用或写入验收；后者仍待验证 | ⚠ 工具接入不等于人格自动注入；自动注入单独核 | 见下方「ChatGPT Secure MCP Tunnel」 |
| **其它聊天端** | ⚠ **未实测、需确认 MCP 支持状态**；不能借用 ChatGPT、claude.ai 或 Grok 三格中任何一格的成色。⚠ **也别默认它跟 grok.com 一样强制 OAuth 发现**——那条当前只有一例（grok.com），**claude.ai 自定义 Connector 是否同样要求，本项目未验** | ⚠ 逐家确认 | 逐家查官方文档 |
| **claude.ai 网页／手机 App 的聊天窗口** |  **已通过 VPS 远程 MCP Connector 接通**（判据与采集条件见下面「claude.ai Connector 那一格」；写回落盘与跨窗检索命中也已跑通）；本地 stdio 仍不能直连，必须走公网 HTTPS 的 Streamable HTTP 服务 | ⚠ 不自动注入——Connector 只给工具；人格要手工贴（同桌面 App 那格的形态） | 见下面「为什么」＋部署形态二 |

### 为什么本地 stdio 不能直连聊天窗口，但 VPS Connector 可以

现在的准确说法是：**默认的本地 stdio 不能直连，但部署到 VPS 的远程 MCP 已经通过
claude.ai 自定义 Connector 接通了。**两句话不冲突，区别在于
服务从哪里运行、有没有公网 HTTPS 地址。具体部署边界见部署形态二末尾
「claude.ai Connector 那一格」。

不是没配对，是**两边说的根本不是同一种 MCP**：

- **默认档是本地 stdio 服务**——一个跑在你自己机器上的 Python 进程，
  靠标准输入输出（stdin/stdout）跟客户端通信。**它没有网址。**
- **claude.ai 网页与手机 App 的 Connector 只接远程 MCP**——要一个公网可达的
  HTTPS 地址。它是从 Anthropic 的服务器去连的，**够不到你家那台机器上的进程**。

所以这不是"改个设置"能解决的，中间缺的是一个公网地址。

**那把它改成 HTTP 服务不就行了？** 换传输只是第一步，后面还有三样，
决定之前先看清楚：

1. **要有公网 HTTPS**：一个域名、证书、一台一直开着的机器。⚠ 这三样的门槛没有听上去那么高
   ——域名可以用 sslip.io 免掉，1 GB 的小机器加 swap 也够，**两条各自的代价**见部署形态二；
2. **要有鉴权**。Connector 那条路是公开可达的，**不加鉴权等于把你的记忆库
   挂在公网上**；
3. **语料会离开本机**。默认档整套设计的前提是"语料不出本机"，走这条路就是
   放弃这个前提——这是产品判断，不是技术细节，**得你自己明确点头**。

`mcp_server.py` 同时支持本地 stdio 与原生 Streamable HTTP
（`--http`＋`--token`，鉴权内置），只认 HTTP 的客户端可以直连
（手机前端真机上走通过：Kelivo，见下面「部署形态二」）。
上面那三条代价照样一条不少——换传输省的是搭建，不是省判断。

### ChatGPT Secure MCP Tunnel（State Ledger 读链路已真机接通）

这条路与上面的公网部署不同：OpenAI 官方 [Secure MCP Tunnel 指南](https://developers.openai.com/api/docs/guides/secure-mcp-tunnels)
允许 tunnel-client 从本机主动建立出站 HTTPS，再把 ChatGPT 的 MCP 请求转给回环地址；
`mcp_server.py` 不开放公网入站端口。⚠ **这不等于数据不离机**：工具请求与返回的记忆内容
仍经过 OpenAI，并适用账号／产品侧的数据与日志政策。电脑、记忆服务与 tunnel-client
在调用期间都要保持运行。

1. 从 OpenAI Platform 的 Tunnels、Runtime API keys 与 ChatGPT Connectors 原始页面取得
   tunnel ID、运行时 key 与账号权限。**这些值不写进仓库、文档或聊天记录。**安装官方
   tunnel-client 后先运行 `tunnel-client help quickstart`；下载与权限入口以官方指南为准。
2. 在仓库根目录启动只绑定回环的 MCP HTTP；这条最短路径不配 `--token`，含义是**信任同一
   主机上的进程环境**——回环只挡远端入站，同机其它进程仍能直接读写这个 MCP。不要在
   多用户或存在不受信进程的主机上照抄，也**不要把 HOST 改成 `0.0.0.0`**：

   ```powershell
   python 记忆协议/src/mcp_server.py --corpus <叙事语料目录> --http 127.0.0.1:8765
   ```

3. 另开终端创建本机 profile、预检并前台运行；示例中的 tunnel ID 去原始来源取，运行时 key
   按官方说明放环境变量，不把明文 key 填进命令或 profile：

   ```powershell
   tunnel-client init --sample sample_mcp_remote_no_auth --profile latent-chatgpt --tunnel-id <去 OpenAI Platform 取> --mcp-server-url http://127.0.0.1:8765/mcp
   tunnel-client doctor --profile latent-chatgpt --explain
   tunnel-client run --profile latent-chatgpt
   ```

4. `doctor` 通过且 `run` 保持健康时，再到 ChatGPT Connectors 选择同一个 tunnel、刷新工具。
   基于 Latent 的独立 State Ledger 部署已由 ChatGPT Work 新窗口真机成功调用 `state_session_start` 并读到跨窗接力便签，证明 Secure MCP Tunnel 的实际读链路可用。验收仍不能只看“连接成功”绿灯：本项目六个 `latent_*` 工具须逐个确认可见并真实调用，另做一次 `latent_append` 写入、换新对话后 `latent_search` 命中；这些尚未验证项不从 State Ledger 的 `state_*` 结果推定。

本轮刻意不做 OAuth，也不改变 Claude 使用的 Bearer token 链路。Secure MCP Tunnel 解决的是
网络可达性，不等于终端用户授权；将来若做多用户服务，再按 MCP OAuth 2.1 单独设计。

### 闭源前端这一类（Kelivo / Operit）：能接，但只兑现一半

客户端其实是三类，不是两类：

| 类 | 特征 | 代表 |
|---|---|---|
| **有宿主** | 自动读约定文件名的人格文件 | Claude Code、Codex |
| **闭源前端** | 能接 MCP，但**不读你的文件**，只注入它自己的配置项；而且**改不了代码** | Kelivo、Operit |
| **自建前端** | 两样都得自己实现，但**代码在你手里** | 见 §4b 与《注入契约》 |

中间这一类不像有宿主的那样自动，也不像自建的那样可以自己补。上面表里
Kelivo / Operit 两行的意思展开说就是：

- **检索那一半能用，而且有两条路，⚠ 先看第一条**：
  1. **客户端在手机本机按 stdio 拉起 server**——**不用服务器、不用域名、不用证书、
     不用鉴权，语料根本不离开手机**。**Operit（Android）实测跑通过这条**
     （proot Ubuntu，当时五个业务工具全接通＋端到端写回），见下面「部署形态一」。
     ⚠ **Kelivo（iOS）走不了这条**（没有 proot 那类环境），两家别混为一谈。
  2. **拉不起 stdio 才走公网**：server 原生 `--http` 直连（见下面「部署形态二」）。
  ⚠ **别把这类前端一概读成「必须有公网服务器」**——那只对拉不起 stdio 的客户端
  （比如 iOS 上的 Kelivo）成立。
- **人格那一半不会自动生效**：Operit 实测**不注入工作区文件**（在人格文件里
  塞暗号、新会话答不上来，模型主动翻文件才找到），它每轮拼进 system prompt 的
  只是自己内置的偏好字段。**容量不是问题**：手动粘贴没有硬上限（实用上限约 20 万
  字符起卡，见上表那行）；Kelivo 要手工用文件导入进
  system prompt，**容量同样不用担心**（实测 10M 字符仍不截断，真实人格文件
  低三个数量级）。**手工补上人格是这类前端上的必需步骤，
  不是可选优化**——只接 MCP 不补人格，模型不认识你。
  ⚠ **但「连该去查记忆都不知道」这半有反例，别照抄**：Claude 桌面 App
  上实测 4 个新窗（带 profile 2 个、不带 2 个），**开场召回 `latent_session_start` 4/4 都调了**——
  开场那一次靠工具描述就能驱动，不靠人格。⚠ **按需检索是另一回事**：那一半要靠
  人格里那句 disclaimer 压住片段（见下面「⚠ 人格里的对话片段有挤掉检索的倾向」）。
  两件事分开看，别用开场那个 4/4 当「主动性有了」。

**补人格用出货里的第四件：`引导句.txt`（小字段放指针、全文留文件）。**
两家实测都贴得下人格全文，所以**指针换来的不是容量，是「改了人格文件不用重贴全文」**。
引导句只说两件事：先读哪个文件
（绝对路径，出货时已填好）、什么时候读（每次对话开始）。把它原样贴进 App 的
自定义指令／角色描述／system prompt 框就行，人格全文留在文件里由模型按引导去读。

三条边界，贴之前读一遍：

- **别往引导句里加内容**。它是一句指针，不是「第二份人格文件」——性格、语气、
  边界都在人格文件里，往指针里塞就等于维护两份人格，两份还会不一致。
- **它换来的不是「每轮都在」**。人格从常驻变成了按需读取，《注入契约》第二条
  在这类前端上仍然不满足——它换来的只是「模型有机会知道去读」。
- ⚠ **这条指针路线未经实测**；验法照抄暗号
  测试——暗号放人格文件、引导句贴设置字段，开全新会话问暗号，**不经提示答上来
  才算生效**。验了欢迎回来说一声，这里照实改。指针不生效、或 App 读不到那份文件时
  的退路是把人格全文手工贴／导入进去，**容量验过了**：
  Kelivo 的文件导入 10M 字符不截断，Operit 的粘贴框没有硬上限（实用上限约 20 万
  字符，到那个量级保存会非常卡、再加会让 App 强制重启）。**两家都贴得下一份人格
  文件**，这条退路是通的；代价是**改了要手工重贴**。

两个前端值得分开看：Kelivo 被传输类型不匹配卡过（要在配置里明确选
Streamable HTTP），Operit 两种传输、两种鉴权姿势都吃。

成色声明：这一类的结论都是在真机上验的，环境逐行写在上面那张表里；
一手记录留在项目内部的实测存档里（不随包），本节已把结论完整转述，没有留在存档里
才看得到的关键信息。

### 部署形态一：客户端在本机拉起 stdio（**先试这条，不用域名、不用证书、不用鉴权**）

**实测跑通（Operit ＋ Android 上的 proot Ubuntu）**：语料库和 server
都在手机本机，客户端**自己按 stdio 拉起** `mcp_server.py`，不经公网。
这条路上**下一节那三样代价（域名／证书／鉴权）一条都不用付**，因为根本没有对外端口。

实测成色：当时的五个业务工具全部接通可用（`latent_search` / `latent_session_start` /
`latent_append` / `latent_correct` / `latent_thread_close`），`latent_append` 写入后
**新开会话仍能检索命中**——这是闭源前端上的端到端写回记录。
当前工具表另有 `latent_unresolved`；照显式白名单接入时必须把它一并列入，但上述旧实测
发生在该工具加入之前，更不能把五工具记录追认成当前七工具全量通过。

⚠ **2026.08.21 补一条边界：这条路在 proot 容器里的 Python 上没跑通。**
一位外部用户（Android ＋ proot Ubuntu ＋ Python 3.12.3 ＋ Operit 1.12.1+）按 stdio 配，
**Operit 管理页显示「已部署」，对话界面工具列表却是空的**，
`~/.memory-mcp/last-startup-error.log` 也不存在（＝进程压根没被拉起）。
⚠ **别读成「proot 里跑不了 stdio」——上面那条 08.03 的记录就是 proot**
（Android ＋ proot Ubuntu，由客户端按 stdio 拉起）。
同一个宿主、同一种容器形态，一次成一次不成，**所以差别在配置怎么写，不在 proot**。

**两次记录在案的差别只有两处，都还没验过，别照着任何一条下结论**：

1. **`command` 的写法**：08.03 写的是 **proot 内 venv 里的 python**，
   08.21 写的是裸字符串 `"python3"`。⚠ 所以更收得住的说法是
   **「裸命令名解析不到」**，不是「proot 整个不可见」。
2. **配置结构**：08.03 那份 `mcp_config.json` 是从 claude-code 出货产物适配来的

⚠ **别信「Operit 看不见 proot 里的 python」这个说法**——它是我方当时凭现象给的解释，

**照它去改配置很可能白改。** 稳妥的做法是先照第 1、2 条改（`command` 写绝对路径或
venv python、配置带 `mcpServers` 外层），不行再走下面的「形态一之二」。若你装的是 **Termux 原生 Python**（不是 proot 里那个），
stdio 需要把 `command` 写成**绝对路径**（形如
`/data/data/com.termux/files/usr/bin/python3`），`args` 里的路径也全写绝对——
⚠ **这条路外部报告提过，但没人真跑过，本项目也未复现。**

### 部署形态一之二：同机回环 HTTP（**proot 用户走这条**，2026.08.21 外部实测跑通）

不出网、不要域名、不要证书——跟形态二完全不是一回事。做法是**你自己在容器里把服务
起起来**，客户端当远程 MCP 连 `127.0.0.1`：

```
python3 <绝对路径>/mcp_server.py   --corpus <绝对路径>/corpus   --threads <绝对路径>/threads.jsonl   --http 127.0.0.1:8765 --token <一串你自己定的口令>   --timezone Asia/Shanghai &
```

客户端侧填 `http://127.0.0.1:8765/mcp` ＋ 同一个 token（Operit 在**远程／HTTP 标签页**）。

- ⚠ **路径全部写绝对**——形态一那条相对路径的坑在这里同样会咬。
- **proot 容器与 Android 应用共享回环地址，不用做端口映射**（实测）。
- ⚠ **代价是要人手动起**：容器里那个进程一关，服务就停，客户端配置不用改但连不上了。
  写个启动脚本，重启后跑一次。
- ⚠ **`--token` 不是可选的装饰**：回环只挡远端入站，**同一台设备上的其它应用仍连得到**。
- 判据仍是「文件真落盘 ＋ 检索真命中」，不看日志。

⚠ **成色**：外部实测转录（Operit 1.12.1+／Android／proot Ubuntu／Python 3.12.3，
**代码基线 commit 未给**），**本项目未复现**。

⚠ 三条跟宿主拉起有关的坑，都是实测撞出来的：

- **别自己 `nohup` 起后台进程**——stdio 传输要 stdin，手动起会当场崩
  （`Bad file descriptor`）。**这个 server 只能由客户端宿主拉起**，
  “先手动跑起来试试”在这条路上是错的做法。
- **懒加载**：调用时才拉起进程，用完连接关闭、进程退出。好处是**每次调用都重读
  一次语料目录**，手动加进去的 md 下一次调用就看得到。
- **别拿客户端的 `lastStartTime` 判断跑没跑通**——它只在显式连接时更新。
  **判据用“文件真落盘 + 检索真命中”**，这两样才是结果。
- **这条路上终端里不会有任何请求日志，那不是没跑通**——stdio 没有端口、
  没有常驻进程，调用时才被拉起、用完就退出。⚠ 尤其别拿“HTTP 终端没收到
  `latent_search` 的请求”当证据：**那是另一种部署形态（形态二）才会有的东西**，
  在这条路上它**永远**不会出现。判据同上一条，看落盘和命中，不看日志。

- **起不来的时候，客户端只会说「连接失败」，但服务端会想办法把话说给你听**：
  stdio 这条路上服务端的报错打在 stderr 上，多数客户端不转发，
  于是用户手上只有那四个字。现在启动失败**不再直接死掉**——服务端会照常跟客户端握手，
  把「为什么起不来 ＋ 下一步该做什么」放进模型的上下文里，**你直接问一句
  「记忆库能用吗」就能问出来**；模型这时调任何记忆工具，拿到的也是同一段话。
  ⚠ **这时客户端多半显示「已连接」，但记忆库是真的用不了**——那个壳一个能干活的
  工具都不提供，别当成连通了。同一段话连完整报错还会写进
  `~/.memory-mcp/last-startup-error.log`（可用环境变量 `MEMORY_MCP_LOG_DIR` 改目录），
  排查时**直接把那个文件贴出来**即可。
- **语料很大时，第一次启动会慢，那不是卡死**：握手前要先把全库读完建索引。
  超过 5 秒服务端会打一行「正在读语料建索引……」（在能看到终端的形态下看得见）。
  ⚠ 这段时间客户端那头确实可能超时，**首次启动最慢，之后会快一些**。

成色声明：只验过 Operit 一家、只在 Android 上；Kelivo 侧未测。
⚠ **上面「起不来时」那两条的成色，分开说**：
**已验**——Windows 桌面机上 `claude mcp list` 两行并排：起得来的那份显示
`√ Connected`（那就是降级壳），故意配坏的那份显示 `× Failed to connect`
（采集条件：Windows／Claude Code CLI `2.1.223`；⚠ Windows 上没有 `python3`，
配置里的 `command` 要就地写成 `python`）。
**未验**——模型硬去调一个记忆工具时会看到什么。这一条在这两个客户端上**够不着**
（Claude Code 不会把不在工具表里的名字交给模型；HTTP 那条形态上根本没有这个壳），
⚠ **"没触发过"不等于"验过了"**，照实说。

### 部署形态二：公网 HTTP 服务（server 原生支持；**绑定地址与 TLS 两条要看清**）

⚠ **先说边界：这不是推荐路径。** 默认档的前提是「语料不出本机」，而这条路上
语料放在你的服务器上、模型多半走第三方 API——上一节第 3 条的代价在这条路上
**是已经发生的事实，不是风险提示**。这是你自己判断后走的路，下面只讲怎么走得稳。

**server 原生支持 Streamable HTTP**，一行命令起服务。

⚠ **这条路上 `--timezone` 从"建议"变成"必须写"**（上面「时区那一行」那节讲了机制）：
服务器在机房、你在你自己的时区，这两个不是一回事。**默认值是东八区，所以只有你确实
在东八区时不写才没事**；不在的话，你每天凌晨那几个小时记下的记忆会被静默记成前一天。下面每条命令示例里
都省略了它，抄的时候自己把 `--timezone <你的 IANA 时区>` 加上。

⚠ **`--http` 的参数是 `[HOST:]PORT`，先决定绑哪个地址再抄命令**——省略 HOST
只绑 `127.0.0.1`，**别的机器（比如你手机上的 App）连不到**：手机连不上时，
这里是第一个要查的地方，不是协议。两种绑法都在下面，**代价不一样**：

**① 推荐：服务绑回环，公网那一跳交给反代管 TLS**

```
python3 mcp_server.py --corpus <语料目录> --http 127.0.0.1:8765 --token <一串你自己定的口令>
```

代价：要准备**一个 HTTPS 域名 + 反代（Caddy／nginx）**（下面「证书」那条说了为什么自签不行）。
换来的是**公网上跑的是 HTTPS**——token 和检索回来的记忆内容不在网上裸奔。
客户端里填 `https://你的域名/mcp`。

⚠ **域名不是非买不可，机器也不用大**（外部实测转录，本项目未复现）：

- **sslip.io 能免掉买域名这一步**：这类通配 DNS 服务把 `<公网IPv4>` 直接编进主机名，
  Caddy 照常能为 `memory.<公网IPv4>.sslip.io` 签下 Let's Encrypt 证书，外网 HTTPS 正常。
  **代价要一起看**：主机名里明摆着你的公网 IP，**IP 一变，连接器 URL 就得跟着改**
  （换机、重建实例、动态地址都会踩）。
- **1 GB 内存的 VPS 加上 swap 可以稳定运行**（实测环境是 1 vCPU／1 GB、Ubuntu 24.04、
  systemd 常驻）。写在这儿是因为「一台一直开着的机器」容易被读成要台大机器。

<details>
<summary><strong>② 不推荐：临时排查绑定地址时，直接绑所有网卡</strong></summary>

下面这条只用于短时确认“连不上是不是因为服务只绑了回环”。它不是正式部署模板；
需要长期运行就用上面的 `127.0.0.1`＋HTTPS 反代。

```
python3 mcp_server.py --corpus <语料目录> --http 0.0.0.0:8765 --token <一串你自己定的口令>
```

代价：这是**裸 HTTP 暴露在公网、没有 TLS**——token 与 `latent_search` 返回的记忆
内容**全程明文**，路上任何一跳都能看见，拿到 token 的人既能读全库、也能
`latent_append` 写进去（写进去的东西下次会话会被当成真实记忆读出来）。
所以这条**只用来临时验证「是不是绑定地址的问题」**，而且要付两笔：
**上防火墙限制来源**，事后**把那个 token 当已经泄露过来处理**（换一串）。
⚠ **绑非回环地址时起动横幅会多打一行 TLS 提醒**——那行不是报错，
服务照常起（挡住「临时验证」这条路本身就是错的），但它每次都会打，**配了 token 也照打**：
token 管的是「谁能调」，TLS 管的是「路上谁能看见」，两件事。

</details>

客户端里填 `http(s)://<你的地址>/mcp` 和这个 token（Kelivo/Operit 都支持
bearerToken／Authorization 头，Operit 有源码佐证）。要点四条：

- **鉴权内置且是硬的**：`latent_search` 读全库、`latent_append` 能写入——
  端口被扫到，记忆库既可读又可写，写进去的东西下次会话会被当成真实记忆读出来。
  所以**绑非回环地址必须配 token，否则 server 直接拒绝起动**（这不是可以跳过的
  警告）。「先跑通再说」地开无鉴权端口不存在了——想裸跑只能绑 `127.0.0.1`，
  那是留给前面套带鉴权反向代理的形态。
- **证书**：**域名 + Caddy + Let's Encrypt**，server 自己不做 TLS（反代顺手管了）。
  自签证书这条路**不通**：Operit 与 Kelivo 两次独立实测都不认自签（Operit 那次
  有完整对照实验——Node 标准 TLS 校验，自签报 `DEPTH_ZERO_SELF_SIGNED_CERT`，
  `curl` 交叉复核一致；Kelivo 结论相同）。两个独立 App 同一个结论，
  这是这类前端的**共性**：走这条路就要准备一个域名。唯一的绕法是全局关闭证书
  校验，等于把 TLS 关掉，不该做。
- **手动加语料不用重启**：常驻形态下 server 检测到语料目录文件变化会**自动
  从盘上重读**。`--doctor` 报的块数与常驻内存里的短暂对不上时，发一次任意检索
  就同步了。
- **连不上先看服务端那一行**：客户端那边被拒时多半只显示
  「Transport disconnected」一类的通用失败，看不出是哪一种拒绝。现在**server 每拒一次
  就在自己的终端（stderr）上留一行**，形如
  `被拒 404 GET /nope 来自 203.0.113.7：没有这个端点`——含状态码、方法、路径、
  来源 IP 和原因，路径少写 `/mcp`（404）、token 抄漏一位（401）、客户端默认开了
  分块上传（501）在这里是三行不同的字。**正常请求照旧一行都不打**，所以终端上
  有东西就是有请求被拒了。
  ⚠ 这行**故意不打 token、也不打请求体**（请求体里是你的问句和要写入的记忆），
  所以它能直接贴出来找人帮看；路径也剥掉了 `?` 后面那截。
  ⚠ 被扫的时候（绑了 `0.0.0.0` 就会被扫）每分钟最多逐条打 60 行，压掉的那些
  会在下一行汇总成「过去一分钟另有 X 条被拒未逐条列出」，**不会闷声压掉**。
- **连续重试会不会限流**：本 server 当前没有调用次数上限、冷却计时或 429；快速调用只会在
  HTTP 进程内串行排队。反向代理、托管平台和客户端可能另有超时或限流，要看它们各自日志。
  `latent_session_start` 真空库会明确说「记忆库是空的」；读取或解析异常会自动重试一次，仍失败则
  返回非空 `isError` 与失败类型，不会由 server 合法地返回空文本。
  ⚠ **边界**：有一例外部反馈报告过开场召回连续三次空白，现场日志拿不到、我方未复现，
  所以**别把这条保证倒推成「那三次一定是文件读取失败」**——它挡的是这一类失败被静默成
  空结果，不是「已经查明那次是什么」。
- **传输**：只说 Streamable HTTP（POST 单条消息），不提供 SSE 长流；
  客户端侧要选 Streamable HTTP。
- ⚠ **工具名撞上宿主自带的同名工具时，会是一次零报错的失败**：服务连着、
  工具列表看得见、模型照常回话，只是它调的不是这一份。本项目当前七个工具因此
  都带 `latent_` 前缀（`latent_search`／`latent_session_start`／`latent_append`／
  `latent_correct`／`latent_cleanup`／`latent_unresolved`／`latent_thread_close`）。**有一例外部实测支撑这条**：
  一位 Kelivo 用户在旧版（无前缀）上连不上，**把工具名自定义之后就能正常用了**
  （外部自述，本项目未复现；⚠ 他改成了什么名字、客户端版本这些没记全，
  只当方向性证据）。⚠ **从无前缀的旧版本升上来的话，人格文件／`CLAUDE.md` 里
  写死的旧工具名要跟着改**，否则模型会去调一个不存在的工具。
- **传输**：Streamable HTTP（POST 单条消息）；客户端侧要选 Streamable HTTP。
  服务端**按客户端的 `Accept` 头给形态**，两边都覆盖：
  - 客户端**明确只收** `text/event-stream` 时，那条响应包成单事件 SSE
    （`event: message` ＋ `data:`）；`Accept` 里同时写了 `application/json`
    （规格要求客户端两个都写）或写 `*/*`、或没带这个头，一律回 `application/json`。
  - **GET 会得到一条只发心跳、永不发消息的空长流**。本服务没有服务器主动推送的
    场景，这条流上一条消息都不会走——它存在的理由是：有的客户端先发 GET 建长流，
    收到 405 之后**不改用 POST**，就卡在等长流上，表现是「连不上」。
    客户端明确只要 JSON 时才回 405。
  - 不想要这条长流就加 `--no-sse-stream`，退回「GET 恒 405」。
    ⚠ 那种情况下，不会回退的客户端仍然会卡住——这一点服务端会在 405 那行日志里说。
  - 长流同时最多 4 条，开满了回 405（日志里会说是开满了，不是别的原因）。

**成色声明（照实）**：盖着这条路的判据有两层，**分开说**——
① `mcp_server.py --selftest` 第 18 项：真端口、但**同进程起线程**
（鉴权 401、非回环拒绝起动、非 ASCII token 拒绝、Origin 403、chunked 501、
keep-alive 下被拒后重试、UTF-8 写回即查、语料变化自动重读、**被拒的请求在服务端
留一行／正常请求不留、token 与请求体不进日志、刷屏上限与溢出计数**）；这一项里
**只有 TLS 提醒那一格是另起真进程量的**（横幅在 `__main__` 里打，同进程起线程
盖不到它；两个绑法各起一次进程，断非回环打、回环不打）；
② `e2e_smoke.py`：**另起进程**跑 `--http`、裸 socket 走握手→写回→复用连接检索，
并在子进程退出后回读文件确认**真的落盘**。
** Kelivo 真机走通过**（Kelivo 1.1.17 iOS ／ VPS Ubuntu ＋
Python 3.10.12；`ss` 确认端口上蹲的是 `python3`，POST 回的是
`application/json`）。**Operit 侧没有人在这条路上试过。**

⚠ 两条**得的是「没踩到」不是「不存在」**：`Origin` 403 与 GET 长流 405 这两条
在那次真机上都没被触发（说明 Kelivo 不发 `Origin`、也不强依赖 SSE 长流），
换个客户端仍可能踩。谁在别的真机上走通了或卡住了，欢迎回来说一声，这段照实改。

⚠ **`Accept` 协商与 GET 空长流那两条（上面「传输」那格）目前只有自检盖着，
没有真机**：自检是真端口往返，量的是**服务端形态已具备**——只要 SSE 的 POST
确实回 SSE 帧、GET 确实拿得到长流、心跳确实在发、并发上限确实拦得住。
**它不证明任何一个客户端因此接上了**。手上有卡在「一直连不上」的客户端的话，
这条路值得试，试完请回来说结果。

### 不会 SSH、想用云主机网页控制台部署？先看这三条坑

一位非开发者用户全程在 Vultr 的浏览器 noVNC 控制台里完成部署，踩到三条**都不报错、
都让人以为是自己命令敲错了**的坑（外部实测转录，本项目未复现）：

1. **剪贴板会把长脚本当成 login 密码打进去**——表现是反复 `Login incorrect`，
   看起来像密码错了，其实是那一大段脚本被喂进了用户名／密码输入框。
2. **`Ctrl+V` 在 noVNC 里变成字面量 `^V`**——要用 noVNC 自带的 Clipboard 注入框，
   或者按 `Shift+Insert`。
3. **长 heredoc 里的中文在 noVNC 里会乱码**——写完先跑一次
   `python3 -m py_compile <文件>` 自检，别等运行时才发现。

**结论一句话：不要在浏览器 Console 里贴长脚本，用系统自带的 SSH。**
（Windows 10／11、macOS、Linux 都自带 `ssh` 命令，不用装额外软件。）

⚠ **本项目不提供、也不打算提供「单行 `curl \| bash`」安装。**
这套东西的卖点是零依赖与语料不出本机，而 `curl \| bash` 要求你在读到脚本内容之前
就把 root shell 交给一个远端 URL——**那是拿信任换方便**。上面三条坑的正解是换成 SSH，
不是把一条更难审计的路径包装得更短。

### claude.ai Connector 那一格（capability URL 路线已实测接通）

claude.ai 的自定义 Connector 本质就是「填一个远程 MCP 服务器的 URL」
（[官方文档](https://claude.com/docs/connectors/custom/remote-mcp)、
[帮助中心](https://support.claude.com/en/articles/11175166-get-started-with-custom-connectors-using-remote-mcp)），
全部订阅档位可加（Free 限 1 个），手机 App 也认。**维护者把服务部署到自己的 VPS，
用下面第二条那个 capability URL 形态接通了 Connector。**⚠ 要看清是**怎么**满足的：
公网可达（Anthropic 的服务器来连）与 Streamable HTTP（`--http`）是直接满足的，
**鉴权那一项不是靠官方入口满足的，是靠那段随机路径顶上的**。逐条：

- 官方有一个 **Request headers** 功能能直接配 `Authorization: Bearer <token>`，
  跟 `--token` 的形态一字不差、服务端一行不用改——**但它在 beta、逐步放量**：
  实测数据点（维护者账号）添加对话框的 Advanced settings 里
  **只有 OAuth Client ID/Secret 两栏，没有 Request headers 区**。
  没被放量到的话走下面这条，**不是 OAuth**。
- **实际走通的就是这条：把口令藏进 URL**（capability URL）：
  server 绑回环裸跑（`--http 127.0.0.1:8765`，不配 token——`http_bind_guard`
  给「反代在前」的形态留的就是这个门），Caddy 只把一段长随机路径转发进来：

  ```
  你的域名 {
      handle /<一长串随机字符>/mcp {
          rewrite * /mcp
          reverse_proxy 127.0.0.1:8765
      }
      handle {
          respond 404
      }
  }
  ```

  Connector 里填 `https://你的域名/<那串随机字符>/mcp`。
  （维护者那台走通时用的是 **nginx**，不是 Caddy——形态一样：只精确命中那一段
  随机路径才转发进来，其余一律 404。反代软件换成哪个都行。）
  ⚠ **那串随机字符就是密码**：谁拿到完整 URL 谁就能读能写这个记忆库。
  别写进仓库、别截图、别贴进公开日志。
  ⚠ 弱点照实说：URL 会进各种日志（浏览器、代理、对端），比 header 里的
  Bearer 弱一档——当**可撤销的口令**用，怀疑泄了就换一段路径。
  等 Request headers 放量到你的账号，就换回干净的 `/mcp` + 正经 Bearer。
- **不要**无鉴权直接填 URL——大概率也「能连上」，但那等于把记忆库可读可写地
  挂在公网，正是 `http_bind_guard` 拒绝起动挡的那个形态。
- 给 server 补 OAuth（401 challenge + resource metadata + 授权服务器）**不做**：
  安全敏感的一整套、跟零依赖路线冲突，为一个 beta 迟早覆盖的缺口不值得。
  ⚠ **这条判断是就 claude.ai 这一格说的，仍然作数**；grok.com 那一格的情况不一样
  （它**强制**要 OAuth 发现层，见下一节）。**别把两家合并成一句「网页端都要 OAuth」**
  ——claude.ai 是否也强制要求，本项目未验，那边走通的 capability URL 路线
  **根本没走到弹凭据表那一步**。

**成色（照实，判据与采集条件一起写）**：

- **判据**（开测前先写下的）：新开一个窗口、开头**只喊一句称呼**，
  **看到换窗召回（`latent_session_start`）被主动调起来**，就算这一格通；
  界面上「已连接」的绿灯不算。
- **数**：**3/3**——三个新窗口全部主动调起来了。
- **采集条件**：维护者本人的 claude.ai 账号与自定义 Connector；
  服务跑在维护者自己的 VPS 上，`--http` 绑回环、**server 侧不配 token**，
  由 nginx 精确匹配一段高熵随机路径转发；入口 URL 本身是凭证，**不入库**
  （要用去原始来源取）。
- `latent_append` 写回落盘、跨窗检索命中，**在这条路线上也已跑通**
  （维护者本人实测；这两项没有像上面那样留下逐次的数与采集条件）。
- 这条结果同样不外推成性能与长期稳定性。Connector 仍只解决检索工具这一半：
  人格不会自动注入，要像桌面 App 那格一样手工贴，改了也要重贴。

### grok.com 网页 Connector 那一格（强制 OAuth 发现层；接通那一例靠用户自建 shim）

**先说清这一格现在是什么成色**：一位外部用户 2026.08.21 报告他把本项目部署到自己的
VPS 后，用 grok.com 的账号级 Custom Connector 接通了，当时五个业务工具可用，新 Project 窗口里
开场召回与写入都跑通。**这是外部实测转录，本项目未复现**；而且**接通那一步不是纯靠本
项目现有的 Bearer token 走成的**，逐条看：

- **grok.com 强制 OAuth 发现，没有静态 API Key 选项。** 在 `grok.com/connectors` 添加
  Custom MCP、只填 MCP URL 时，Grok 会先探测——拿到 401 之后弹出的是 **OAuth 凭据表**
  （客户端 ID、授权端点、令牌端点、PKCE），**界面上没有「API Key ／ 静态 Bearer」这一项**。
  本项目 HTTP 模式给的是静态 `--token`，不提供
  `/.well-known/oauth-authorization-server`、`/authorize`、`/token`、`/register`，
  所以**第一次点不了「保存并连接」**。
- **绕过方式是用户自己写的最小 OAuth shim，属用户侧扩展、不是本项目功能。**
  他在同一台机上另起一个进程，让反代把 `/.well-known/*`、`/authorize`、`/token`、
  `/register` 分流给 shim，其余（含 `/mcp`）仍进本项目；shim 走完 PKCE 之后
  **把那份原有的 token 当 access_token 发出去**，于是 Grok 后续打 `/mcp` 的
  `Authorization: Bearer` 仍走本项目原有逻辑。**本项目源码一行没改。**
  加上 shim 之后第二次添加连接器，只填名字 ＋ MCP URL 就成功了。
- **⚠ 所以这一格的正确读法是**：「本项目作为远程 MCP 能被 grok.com 调用」有一例外部证据，
  但**那一例站在一层用户自己维护的 OAuth shim 上**；没有那层 shim，网页那一格
  当前就是**点不了「保存并连接」**。别把它读成「照文档配好 Bearer 就能接」。
- **`latent_thread_close` 在网页 Grok 上不会被触发**：用户关掉标签时没有回调。
  那位用户是自己在 VPS 上加了个每天零点的定时任务写「收工书签」——**同样是用户侧扩展**。
- **旧窗口（连接器后加的）不稳定自动记**：能在用户明确要求时调工具，但不像新 Project
  窗口那样自发召回。⚠ 报告没给次数与分母，**这条只有方向，没有数**。
- ⚠ **这一格的成色不外借**：Grok Build（CLI）仍是「只核过产出格式、没有真机」，
  xAI API／Remote MCP Tools 仍是「官方文档证明有入口、本项目无实测」。
  它也**不是** `grok-4.5` 的模型服从度数据（没有型号、夹具、独立会话次数、
  主动调用分子／分母），《注入契约》那一格仍写「还没测」。

**本项目本轮不实现 OAuth，也不提供 shim。** 报告方建议仓库直接给一份可选的
MCP OAuth 2.1 最小实现，这条**记下来等第二例**：网页端自定义 Connector 要求 OAuth
发现层，**当前只有 grok.com 这一例**；claude.ai 是否同样要求，本项目未验。

### 桌面 App 那一格

**Claude 桌面 App 支持本地 stdio MCP 服务**（那是 MCP 的标准本地形态，
配置方式跟 §3 同类：在客户端的配置文件里写清命令与参数）。所以如果你要的只是
"在一个聊天界面里用"，**装桌面 App 大概率就够了，不用改任何代码**——
这条比改造服务器省事得多，先试它。

**真机验过了**（Windows，微软商店／MSIX 版）——连上之外，
**当时五个业务工具全在、开场召回 4/4、跨进程写回也通**（⚠ 判据是**完全退出进程**重开还查得到，
不是新开对话窗：`latent_append` 写完会立刻更新内存索引，开新窗查到只证明内存、
没证明落盘）。

⚠ **下面三个坑都是不报错的失败，装商店版的人几乎一定会撞第一个**：

- **商店版的配置文件不在 `%APPDATA%\Claude`**。MSIX 包的写入被虚拟化了，真实路径是
  `%LOCALAPPDATA%\Packages\Claude_pzs8sxrjxfjjc\LocalCache\Roaming\Claude\`。
  照官方文档往 `%APPDATA%\Claude` 放的那份**不会报错，只是永远不被读**——
  又一个“看起来配好了”的静默失败。**先确认你装的是商店版还是官网 .exe 版再挑路径。**
- **别用 VS Code 改这个文件**：受限模式（Restricted Mode）下保存会被**静默拦掉**，
  编辑器不弹错、文件没变、你以为改完了。**用记事本最稳。**
- **改完必须完全退出再开**，不是关窗口——窗口关了进程还在。托盘图标里退出，
  或 `taskkill /F /IM claude.exe`。

**人格注入那一列同日也验了，结论是：能通，但走的不是文件那条路。**

⚠ **出货第四件 `引导句.txt` 在这个客户端上不成立**：那句指针是「先完整读取这个文件：
<绝对路径>」，而**桌面 App chat 模式没有读本地文件的能力**——它手上只有本项目 MCP 给的
六个记忆工具，没有一个能读任意路径（`latent_session_start` 返回的是 thread 块＋召回块，
不含人格）。指针贴进去的结果是**模型读不到、也不报错**。

**实测走法：人格全文贴进 profile（个人偏好），不是 Project instructions。**
project 只在那个 project 里生效，开错地方就静默失效；profile 全局，每个新对话都带着。
代价是**所有对话都带着人格**，包括跟记忆库无关的，这个代价要认。

- **容量不用担心**：实测 **1.6 万字贴进 profile 不报错，且前段／中段／尾段
  分别问都答得上来**（不是只验了「能保存」——静默截断的失败形态是无声的）。
  出货那份人格文件 9891 字节（中文 UTF-8，约 3300 字），实测过的 1.6 万字约合 4.8 万字节，
  **富余约 5 倍**（⚠ 按同一个单位算的；1.6 万字是**测到的下界**，真正的上限没测过）。
- **代价是它不会跟着更新**：人格文件改了要手工重贴，跟 Kelivo 同一个卡点。

⚠ **人格里的对话片段有挤掉检索的倾向，靠一句 disclaimer 压住**：人格里按 §3.3
带的**对话片段**，会让模型在被问到过去的事时倾向于**直接拿片段作答、不去查记忆库**
——答得具体又顺，**其实是在读稿**，而且不报错。危险的地方在于**片段里那些事未必
在库里**。所以本工具生成人格文件时会带上一句 disclaimer：「这几段是风格样本，
不是记忆；对方提到过去的事，先查记忆库」（存储＋注入两处都带，自检守着）。

**带着这句时的实测成色**：

- **判据**（开测前写下的）：拿一件**库里确实没有记录**的事，开全新会话直接问——
  **模型必须先调 `latent_search`**，查不到如实说没有，不许拿片段当答案，语气也不许垮。
  四条都过。⚠ **判的是有没有查，不是答得好不好**：模型自己说「我查了」不算数，
  要看工具调用块里 `latent_search` 真被调起来。
- **采集条件**：Claude 桌面 App（Windows 商店／MSIX 版）；MCP 走
  **本地 stdio**；人格手工贴进 profile；语料快照与靶子事件故意错开，让那件事
  在库里必然没有记录。
- ⚠ **两条边界**：①「删掉这句就该失效」只在自检里验过，真机那侧不是一次受控变异；
  ②那次是**手工把这句贴进人格文件**验的——验到的是「这句话对模型有效」，不是
  「自动追加路径已经过该客户端真机复验」。现在走 `use_original_as_is` 会把它随受管协议
  追加到出货副本；完全不经过本工具时，那句仍不会自己出现，手工补一句同样有效。

跑通了或者卡住了都欢迎回来说一声，这张表会照实改。

## 4. 验证接通了

开一个全新会话，第一句问一件只有你们的历史里才有的事，**别提任何工具字眼**。
接通的标志：模型主动查了记忆再回答，而不是说"我没有相关记录"。

如果它没查：确认会话起在产出目录里（人格文件有没有被读到是主动性的关键，
这是主动性最常见的失败原因）；再确认 `claude mcp list` 里
memory 服务是连着的。

### 接不上、或者不确定配对了没有：先跑体检

把第 3 步那行命令里的参数原样搬过来，加一个 `--doctor`：

```
python <src绝对路径>/mcp_server.py --doctor --corpus <叙事语料目录> --index-dir <产出目录>/memory/index --threads <产出目录>/threads.jsonl
```

它会逐项报：**它实际读的两个绝对路径**（主 `--corpus` 与可选 `--index-dir`；配置里写
相对值时，这里会把它解析开——“我以为它读的是别处”就是这么来的）、读到几个文件、
建了几块、索引层认出来没有、**语料的时间范围（最早～最晚）**、时间戳有多少块只能退到
文件修改时间、三个 JSON sidecar 接上了没有、`未解决.md` 是否可读且格式有效、语料目录写不写得进去（写回要用）、会话线索有没有
落点、**服务端认的是哪个时区**、MCP 握手与工具表、以及**拿你语料自己的标题回查一次**——最后一条是唯一能证明
“这份语料真的查得到”的检查。

**时间范围那一行值得停一秒**：它是第 0 步那个坑（旧导出包停在几周前）在部署之后
唯一还会现形的地方。盯住后面那个日期，问自己一句：我跟 TA 最近一次聊天真的是这天吗？

**写回落点那一行也停一秒**：记忆写回（`latent_append`）同时落在语料目录的
**timeline 层**与索引层。显式配了 `--index-dir` 时摘要写到它指向的独立目录；
旧部署未配时自动落到 `<corpus>/index/`，写回仍会完整校验正文与摘要，不会
降级成只写正文；返回会提醒改用推荐的独立 `--index-dir`。如果你的人格文件里维护着
「按需读取指针」，指针必须盖住 timeline，
不然新长出来的记忆按需读不到，而且不报错（检索工具照样查得到，只是主动翻文件会漏）。

**只读承诺的准确范围**：出货（ship）与 `--doctor` 对语料目录只读。
`latent_append` 是运行期写回，本来就会写 `<corpus>/timeline/`；未配 `--index-dir` 时
写 `<corpus>/index/` 属于同一条写回路径，不改变 ship 与 doctor 的只读承诺。这个兼容落点
**只在未配 `--index-dir` 时生效**；配了就只写独立根。已有 `<corpus>/index/` 文件
继续兼容：`latent_append` 只新增自己的事件摘要，不迁移、不复制、不覆盖、不重排已有文件。

`✗` 是过不去的（先修完再起服务），`⚠` 是“能用，但会悄悄变差”。

**体检只读**：跑完你的语料目录里不会多出任何文件（连 `.weights.json` 那类也不会），
所以在排查故障的时候跑它是安全的，不会给现场加新变量。
唯一的例外说在明处：`--embed` 档不体检（那一档建库会把块向量缓存写进语料目录，
跟“只读”冲突），体检会照实说一句，语料/时间戳/sidecar 那些结论跟检索路线无关、照样作数。

## 5. 三条检索路线（初始化第 5 步选的就是它）

### ⚠ 先说一件关于「改错了怎么办」的事：`latent_correct` 撤的是一块，不是一件事

`latent_correct` 撤回的是**你逐字摘的那一块记录**，不是「这件事」。同一个说法如果
还写在别的记录里，那些记录**不受影响**——它们没被撤，照常在库里。

这在两条路上的表现不一样，**差别是真实的，不是错觉**：

- **主动检索（`latent_search`）**：按相关性排序，你问「TA 那只狗叫什么」时，
  那些讲别的事、只顺带提到旧名字的记录通常排不上去，所以看起来「已经改对了」。
  ⚠ **但那是碰巧问不到**，换个问法（问那些记录本身讲的事）旧说法照样会回来。
- **开场自动浮现（`latent_session_start`）**：**没有 query，按时间新鲜度和权重排**，
  没有相关性这一关。**旧说法只要够新或被翻得够多，就会被直接端到模型面前**——
  而那些旧记录的正文里往往就写着「当下状态：……（旧值）」。

**所以：改过重要的事实之后，再用旧说法查一次，把还提到它的记录一并撤掉。**
（召回块开头那句「同类相关的记忆里，以日期最近的一条为当下状态」能兜住一部分，
但那是**交给模型判断**，不是硬保证。）

 **服务端现在会主动提醒你**：`latent_correct` 撤回成功后，会顺手扫一遍库里还有没有
别的块提到同一说法，命中就在返回里告诉你「还有 N 块提到同一说法（最近：……）」，
并给出下一步（用旧说法再查一次、逐条撤）。⚠ **它只提示、绝不替你自动撤**——
词面命中不等于讲的是同一件事，撤错比给旧值更糟，这条边界守死。

⚠ 这个形状我们在合成语料上复现过、也确认了 `latent_session_start` 那条路**并没有
漏掉撤回账本**（被撤的那一块确实不会再出现）；漏掉的是**同一个事实的其它块**。
边界与采集条件见内部验证卡。


检索有三条路线。**它们最重要的区别不是快慢，是你的语料去哪儿**——按档分开写，
不含糊、不放脚注：

| | 零依赖（默认） | 本地模型 | 云端服务 |
|---|---|---|---|
| 要装什么 | 什么都不用装 | `pip install fastembed`，首次运行下载约 100MB 中文模型 | 不装模型，但要一个第三方 embedding 服务的 API key |
| **语料去哪儿** | **不出本机** | **不出本机**（模型在你自己的 CPU 上跑） | **查询和被检索的内容都会发到你选的那家服务商** |
| 怎么开 | 默认就是 | 第 5 步选 `local` | 第 5 步选 `cloud` |
| 代价 | 无 | 建库和检索都变慢，低配机器（2C2G 这类）感知明显；小内存机器可能装不下 | 每次查询多一个网络往返；块向量只在建库时算一次并缓存在本机，所以日常成本是每查一次一个往返 |

选哪条是你的事，我们不替你拍板，也**不把云端当推荐路径**——默认档是零依赖。

**零依赖与本地模型的实际差别（我们自己的回归集实测，两百块语料）**：

| 查询类型 | 零依赖 | 本地模型 |
|---|---|---|
| 用原话直接问 | 都能答对 | 都能答对（并列） |
| 换个说法问同一件事 | 约四分之三 | 基本都对 |
| 跨很多窗口串起来的事 | 一半多一点 | 略好一些，但两条都还不够好 |
| 库里根本没有的事 | **两条路线都不可靠**（见下方说明） | **同左** |

所以：**平时习惯用原话去问，零依赖完全够用**；经常"记不清原话、只记得大概"才值得升级。

**云端档在这张表里为什么没有一列**：因为我们自己还没在这把尺子上跑过它。有人拿
自己的真实记忆做过一次 20 题的四方案对照，云端模型的成绩跟本地模型不相上下——但
20 题分不出 16 分和 18 分的差别（差 2 题就是差 2 个样本），而且那是别人的语料、
别人的问题。**我们不拿那张表冒充自己的回归集分数。** 你自己想量的话：

```
MEMORY_EMBED_PROVIDER=cloud MEMORY_EMBED_ENDPOINT=<服务商的 /v1/embeddings 地址> \
MEMORY_EMBED_MODEL=<模型名> MEMORY_EMBED_API_KEY=<你的 key> \
python src/regression_set.py --report --embed --embed-provider cloud
```

⚠ **"库里没有就说没有"这件事，三条路线都不可靠**：拿一份六百多块的真实规模
记忆库实测，问一件从没记录过的日常事（某次复诊约在几号这类），系统几乎总能捞回
几条沾边但不相干的记录。所以**检索返回了东西不等于那就是答案**——对不上时最多再查
一次：原问法仍放 `query`，更具体的说法放 `queryVariant`，服务端会融合两种问法；
第二次仍对不上就停并如实说没找到，不循环查到有为止。

**机制那一半有**：候选资格的门槛是"要跟查询共享至少一个区分性词"，不是"词面有分
即可"。但**必须说清它现在的成色**：在我们自己的合成语料上，这条门槛让
"库里没有的事"这一类**一格没涨**——原因不是实现错了，是那份语料量不出来
（能穿透的编造查询靠的是共享真正稀有的词，而词面这一路分不出"共享了一个稀有词的
编造"和"真命中"）。

**真实语料上这一格已经量过了，答案是不会自己变好。****判据**是"库里根本没有答案的
问题，系统有没有正确地空手"——20 道这类题里，**现行实现答对 0 道**。想靠放宽共享词
条件补上，代价立刻显形：改成两字跨度只到 2/20，改成四字跨度能到 18/20，但同一把尺子
上 present 侧开始误杀 5/60、改述召回从 11/15 掉到 7/15、感受类 4/15 掉到 0/15。
**所以现行实现是权衡后选的，不是还没做**：宁可在"库里没有"这一类上交白卷，
也不牺牲"库里有"的那一类。

**采集条件**（换个人拿这份记录重跑要用得上）：151 个 Markdown、经同一版 `load_corpus()`
切成 **794 块**的真实规模语料；present 60 道（literal／改述／linked／感受各 15）＋
absent 20 道，每题恒为 gold=1，护栏留用率 60/60 与 20/20、作废 0；Windows、Python 3.12；
云端 embedding provider `BAAI/bge-m3`，floor 标定 0.60。正文、题面与锚词均未入库。

**对你的实际影响就一句**：这套东西**不会替你挡住"记忆库里没有"这件事**，
所以检索返回了内容不等于那就是答案——对不上就该说对不上，那句话得由人格文件里的
边界条款和你自己来把。

这条门槛唯一可量到的收益出现在**另一类**：跨很多窗口串起来的事（噪声块被挡在候选
之外，排序变干净了）。**"机制没效果"和"效果出现在别处"是两回事**，我们照后者写。

### 云端档要知道的三件事

- **key 只走环境变量**。`MEMORY_EMBED_API_KEY`（要用别的变量名就设
  `MEMORY_EMBED_API_KEY_ENV` 指过去）。我们**不把 key 写进 `mcp-config.json`、
  不存进产出目录、不落任何状态文件**——那个目录你多半会随手分享给别人。
  key 从你自己在服务商那儿申请的账号来，怎么保管是你的事，我们不碰。
- **不内置任何一家的 SDK**。请求走各家通用的 OpenAI 兼容 `/v1/embeddings` 形状，
  换一家只改 `MEMORY_EMBED_ENDPOINT` 和 `MEMORY_EMBED_MODEL` 两个环境变量。
- **换模型必须重新标定命中门槛**。"有没有查到"的判定带一道跟模型绑定的余弦门槛
  （0.45 对应 bge-small-zh-v1.5）。换模型余弦标度就变了，照抄那个数会让
  "库里没有就说没有"无声失灵。所以**没标定过的模型我们不给它一个假门槛**：
  这种情况下向量路只参与排序、不单独放行候选，启动时会明说"未标定"。

  **你自己在自己语料上量过了，可以用 `MEMORY_EMBED_HIT_FLOOR` 传进来**（我们的
  标定表只有 bge-small-zh-v1.5，不想逼你改源码）。但这个口子是给"量过的人"开的，
  不是给"想找个数填上"的人开的：填进去之后 `--describe` 会把它标成
  **"你自己设的覆盖值，不是我们量的"**，出偏差是你的标定不是我们的。
  设歪了（非数字、不在 [-1,1] 内）**当没设处理，绝不落成 0**——门槛为 0 等于门槛
  不存在，那是这条最坏的失效方向。
- **query 侧的指令前缀按模型走**。bge 的中文模型卡要求 query 加指令、passage 不加，
  而 bge-m3 这类明确不需要，硬加反而是噪声。所以我们认模型名（`bge`+`zh` 才加），
  **不按"是不是走云端"来分**——拿 HTTP 端点跑 `bge-small-zh-v1.5` 的人不该被默认掉
  前缀。要自己指定就设 `MEMORY_EMBED_QUERY_PREFIX`（设成空串＝明确不加），
  当前用的是哪一档 `--describe` 会说。

另外：块向量会缓存在语料目录下的 `.embed_cache.json`，建库时算一次，之后每次
起服务只补新增的块——**没有这个缓存，云端档每次开机就是把全库重算一遍**。

**换新会话时的开场召回不花任何云端调用**——这件事我们专门查过，因为那是每开一次
新窗口都要付、而且你正等着第一句话的地方。开场召回按"时间新鲜度 × 用进废退权重"
排序，压根没有查询向量要算，所以三条路线在这一步的代价完全一样（实测：零次调用）。
云端档的往返只发生在**你真的问了一句、系统去检索**的时候。

## 出问题了？

- 每个 `src/*.py` 都带 `python <文件> --selftest`，全绿说明各零件正常；
- `python e2e_smoke.py --selftest` 一口气跑完导入到检索的整条链，红了会指出断在哪一环。
