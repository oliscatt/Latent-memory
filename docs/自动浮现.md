# 自动浮现（Passive Recall）

> 给用户与 AI 看：自动浮现是什么、要不要开、开了会怎样、出问题怎么关。写宿主适配的人另读
> [《自动浮现宿主接入》](自动浮现宿主接入.md)。

自动浮现是一项**默认关闭的可选增强**，不是使用 Latent 的前提：每轮用户消息之后、模型请求发出之前，
由宿主 hook 把几件可能相关的旧事递进本轮输入，让 TA 接话时更像记得你。不启用时，主动检索、换窗召回和正常写回的行为不受任何影响。

它要求宿主能在那个时机执行 hook，并能控制注入内容是否进入对话历史。**“支持 MCP”不等于“支持自动浮现”**：只能挂载工具的客户端提供不了这个时机。
已验证过的宿主见下文[兼容性记录](#兼容性记录怎么看)，每条只证明它自己那个宿主。

**你不需要自己判断这些。** 把本仓库交给你的 AI，让它检查你的宿主是否具备所需能力，并给你一份部署报告；它判断不能确认时会直接告诉你不要开启。
**出问题时先关掉它**，关闭后你不会因此失去任何已有记忆。

## 先把两个名字分开

| 名称 | 什么时候发生 | 谁触发 |
|---|---|---|
| **换窗召回**（`latent_session_start`） | 一场新会话开始时 | 模型按会话约定调用，或宿主在会话生命周期里调用 |
| **自动浮现**（Passive Recall） | 每轮用户消息之后、首个模型请求之前 | 能控制请求生命周期的宿主 hook |

换窗召回已经是 Latent 的常规能力。自动浮现是另一个默认关闭的可选能力；两者不能混称，
也不能用其中一个的实测结果替另一个背书。

## 你只需要回答“要不要开”

把仓库交给 AI 后，AI 应先读取 [`给AI的引导指南.md`](给AI的引导指南.md) 和
[`自动浮现宿主接入.md`](自动浮现宿主接入.md)，替你完成宿主能力判断。它必须确认：

1. 宿主能在用户消息提交之后、首个模型请求发出之前执行 hook；
2. hook 的返回值能进入本轮模型输入；
3. 宿主能控制这份注入内容是否写入对话历史。

三项不能全部确认为“是”时，AI 应直接告诉你“这个宿主不适合启用自动浮现”。它不得替你
开启，也不得在能力不确定时先试。你只需在能力确认后回答是否启用；没有明确回答就保持关闭。

## 两种模式

| 模式 | 会发生什么 | 代价与边界 |
|---|---|---|
| **关闭** | 不做逐轮自动检查与注入 | 主动检索、换窗召回和正常写回照常工作 |
| **临时** | 历史原料只进入本轮请求副本，不进入正常历史 | 推荐；宿主必须真正控制请求副本、保存、恢复与分叉输入 |
| **历史保留** | 少量历史原料追加进当前对话历史 | 后续请求可能重复携带，增加输入与历史占用；关闭不会自动抹掉已经保存的文字 |

两种模式都可用时优先推荐临时模式。只有历史保留模式可用时，AI 必须先说明保留后果，再问你
是否接受；不能替你默认接受。

## 服务端要多准备的两件事

这两件由 AI 替你做，这里写出来是让你知道它们存在：

1. **装 jieba。** 基础功能零第三方依赖，但自动浮现块路径的准入分词要用 jieba：
   `pip install -r requirements-passive.txt`（仓库根目录的这个文件只有一行 `jieba==0.42.1`）。
   没装时服务照常启动；有热词表（可在别处生成后复制过来）就退回子串匹配，没有热词表块路径每轮都留空
   （原因码多为 `low_information`）；事实模式不用 jieba，
   不受影响；主动检索、换窗召回和写回也不受影响。
2. **走 HTTP 时另配一条宿主专用凭证。** 服务端以 Streamable HTTP 运行时，必须同时给
   `--hook-token`（或环境变量 `MEMORY_HTTP_HOOK_TOKEN`）：只有带这条 token 的请求看得见、调得动
   隐藏入口 `latent_passive_recall`。不配时隐藏入口对所有凭证关闭，宿主 hook 自己调用也会得到
   `-32601` 未知工具。`--hook-token` 不能与 `--token` 相同，相同时服务拒绝启动。走 stdio 时不需要
   这一条，但宿主仍要自己把隐藏入口从模型可见的工具表里去掉。

## 事实模式（可选）

自动浮现有两种取材方式，服务端启动时自动选，宿主不用切换：

| 取材方式 | 什么时候用 | 递给模型的是什么 |
|---|---|---|
| **块路径**（默认） | 事实模式没有启用时 | 与本轮话题相关的一段记忆原文 |
| **事实模式** | 开了 `--passive-recall`，并且设了 `LATENT_PASSIVE_FACTS`，或语料目录旁的 `事实库/` 下已有 `全量-…` 子目录 | 与这句话最像的两条一句话事实，外加同一条记忆拆出的另外几条（最多 3 条），是否用上交给回话的模型判断 |

事实模式一旦启用就**完全替代块路径**，两条路不会同时走，也不会互相兜底。

事实库是把已有记忆逐块拆成的一句一条的小事：买了什么、定了什么约定、一句原话、一个具体数字。
块路径要求用户的话和记忆字面上沾边；事实模式按语义找，像“想喝酒”这种没有具体名词的话也能
接上一条相关的旧事。

**怎么开：**

1. 先按上文开好自动浮现，并确认服务端配了向量检索（`--embed`）。事实模式靠向量找相似事实；
   没配 `--embed` 时它每轮都以 `fact_no_embedding` 留空，块路径也不会接替。所以**开事实模式
   必须配向量**。
2. 对你的 AI 说“帮我建事实库”。开了自动浮现后，AI 手里会多出一个 `latent_fact_backfill`
   工具：它每次领一批记忆块，按随附的规则拆成事实交回，服务端逐条校验并记进度。记忆多的话
   要分几次会话才拆得完，中途断了下次接着拆。
3. 全部拆完，AI 调一次 `finish`：服务端去重、生成全量事实库，事实模式当场生效，不用重启。

拆的时候最好用平时聊天的那个 AI、带着你的人格文件：它认得你是谁，拆出来的主语和称呼才对。
拆到一半的内容不会生效，不会出现“只拆了一半就开了事实模式”的情况。服务端没配向量时，回填工具
会直接拒绝开工并说明原因。

以后记忆多了想补拆：再让 AI 跑一遍回填即可。上次处理过的块（包括没拆出事实的）和写回时带过 `facts`
的块都不会再发，只拆新块；新拆的事实与库里同一天的近似事实会被丢掉，不会重复。没有新事实时
不生成新的全量，只把块号记下。

**开了之后：**

- 之后每次正常写回时，AI 可以顺手把新发生的小事拆成事实一起写（`latent_append` 的可选参数
  `facts`），事实库会跟着长。当天写下的事实从第二天起才会浮现。
- 同一条事实递出后 12 小时内不再递。
- 最像的两条之外，同一条记忆拆出的其他事实只要也和这句话沾边，会一起递出（最多再带 3 条），
  同一件事的几个面放在一块给。
- 同一轮里递出同一条记忆拆出的几条“状态”（住哪、在用什么、打算怎样），而且事件日期不同时，较早的
  会标上“这是较早的状态，可能已被更新”。只是标注，旧的照样递；同一天的、单独递出的一条旧状态都不标。
- 撤回（`latent_correct`）或被新事实取代（`latent_supersede`）的记忆，它拆出的事实也不再递。
  这条按事实记下的来源记录号核对；没有记录号、只记了来源文件名的事实，要等那个文件里没有现行记录了才不递。

AI 该不该带 `facts` 只看一条：它的工具里有 `latent_fact_backfill`（开了自动浮现）就带，没有就
不带。带了会追加进 `<语料目录上级>/事实库/增量/<LATENT_FACTS_SIDE，默认 local>/<日期>.jsonl`
（`LATENT_PASSIVE_FACTS` 指向目录时写在那个目录下）；还没建全量时这些事实先攒着，建了全量就会一起用上。
`facts` 格式不对时整次写回被拒，正文也不写；回执里的 `factsStatus=` 说明事实有没有进库。

**怎么关：** 关掉自动浮现就全关了。只想退回块路径的话，把事实库目录里的 `全量-…` 文件夹
挪走或改名，**并且去掉 `LATENT_PASSIVE_FACTS`**，再重启服务。

## 会不会把记忆库搞坏

**不会。自动浮现的检索与注入路径不改记忆正文、索引、撤回／变迁账本，也不会因命中增加记忆权重。**

事实模式另外会写两样运行状态：每次递出事实时更新冷却记录，首次启用时计算事实向量缓存。
它们放在 `~/.cache/latent-passive-facts/`（可用 `LATENT_PASSIVE_FACT_STATE_DIR` 改位置），
不在语料目录里，删掉只会让冷却清零、向量重新计算。

写入自动浮现所需的触发词、原文范围等辅助元数据，只发生在正常的 `latent_append` 或
`latent_supersede` 写回流程中，并复用它们原有的校验；不是自动浮现每轮偷偷写库。事实库只在
两种情况下被写：写回时带了 `facts`，或者你让 AI 用 `latent_fact_backfill` 建库。它放在语料
目录旁边的 `事实库/` 里，不改记忆正文。

自动浮现可能改变的是宿主交给模型的输入：临时模式只改请求副本；历史保留模式会把资料留在
对话历史。可选的观测文件也只有宿主显式配置路径后才写，并且不记录用户输入、记忆原文或模型
回答。最坏情况不是记忆库损坏，而是错误或过期的自动资料留在对话历史里、继续影响回答。
这时先关闭；让 AI 移除旧自动资料，宿主做不到时就新开一个不继承旧片段的会话。

## 装完后，让 AI 给部署报告

不要让用户自己翻日志找成功信号。AI 必须读取宿主配置、实际调用结果与脱敏观测，输出以下
固定格式；不能确认的项写“未确认”，不能用“模型接梗了”代替调用或注入证据。

```text
自动浮现部署报告
- 宿主 hook 时机：具备／不具备／未确认
- hook 名称与实际执行点：<名称；用户消息之后、首个模型请求之前／其他／未确认>
- 当前模式：关闭／临时／历史保留
- 隐藏入口：可调用／不可调用／未确认
- 候选：已取得／空结果／未执行／未确认
- 注入：已完成／未完成／无需注入（空结果）／未确认
- 一句话关闭：<由 AI 可直接执行的关闭方法>
```

“已完成注入”只证明资料进入本轮模型输入；模型有没有自然使用，是另一层结果。空结果也可能是
正常的安全留空，不等于服务坏了。

## 出问题先回滚

对用户的一句话是：**“请关闭自动浮现，并保留其他 Latent 功能。”** AI 收到后应把宿主配置
中的 `passive_recall.enabled` 改为 `false`（或移除自动浮现配置），停止以
`--passive-recall` 开放隐藏入口，并重启对应适配器。参考宿主使用 `passive-recall.json`；
其他宿主由 AI 按实际配置完成同等操作。

关闭后不会再产生新的自动检索、注入或影子处理，主动 `latent_search`、换窗召回
`latent_session_start`、正常写回和已有记忆库完全不受影响。历史保留模式已经写进对话历史的
文字不会随开关自动消失；AI 必须说明是否已移除，不能移除就建议新开不继承旧片段的会话。

## Claude Code：用随包的参考 hook

仓库带了一份 Claude Code 用的参考 hook：`src/claude_code_hook.py`，只用 Python 标准库。它做两件事：

- **换窗召回**（`SessionStart`）：新建、恢复、`/clear`、压缩后都调一次 `latent_session_start`，结果放进
  开场上下文，不靠模型自己想起来调。不开自动浮现也可以单独用这一半。
- **自动浮现**（`UserPromptSubmit`）：设了 `LATENT_PASSIVE_RECALL=on` 时，每条消息提交之后、模型请求
  之前调隐藏入口，服务端组装好就注入。

Claude Code 会把 `UserPromptSubmit` 的输出写进对话记录，所以这是**历史保留**模式：同一条记录一个
会话只注入一次（一轮里有注入过的，只剔掉那几段，其余照常注入）；单轮上限 4000 字节、单会话累计 40000 字节（UTF-8 字节，不是 token），超了就留空。
任何失败都留空，不卡对话。
hook 的输入带 `agent_id`（Claude Code 只在子代理里给这个字段）时，换窗召回和自动浮现都不做；后台子代理、
后台命令的完成通知会作为一轮 `UserPromptSubmit` 进主会话（`prompt` 以 `<task-notification>` 开头），这一轮也不检索。
定时任务、别的会话发来的消息目前没有确定标记，分不出来，照常检索。

它要求 Latent 以 Streamable HTTP 常驻，hook 和 Claude Code 连同一个服务端；纯 stdio 部署用不了。
AI 按下面做：

1. 起服务端，两条 token 不能相同；只要换窗召回的话可以不加 `--hook-token` 和 `--passive-recall`。
   要常驻就交给系统服务，或者保持那个终端开着：

   ```bash
   python3 src/mcp_server.py --corpus <语料目录> --http 127.0.0.1:8765 --token <普通token> --hook-token <宿主专用token> --passive-recall
   ```

2. Claude Code 用**普通** token 连 MCP。之前按《快速上手》§3 配过 stdio 型的 `latent` 的话先把它去掉，
   同一个名字只留 HTTP 这一份：

   ```bash
   claude mcp remove latent
   claude mcp add --transport http latent http://127.0.0.1:8765/mcp --header "Authorization: Bearer <普通token>"
   ```

3. 在用户级 `~/.claude/settings.json`（不会被提交进仓库的地方）加上环境变量和两个 hook。
   `<仓库>` 换成 Latent clone 的绝对路径：

   ```json
   {
     "env": {
       "LATENT_MCP_URL": "http://127.0.0.1:8765/mcp",
       "LATENT_MCP_TOKEN": "<普通token>",
       "LATENT_MCP_HOOK_TOKEN": "<宿主专用token>",
       "LATENT_PASSIVE_RECALL": "on"
     },
     "hooks": {
       "SessionStart": [{"hooks": [{"type": "command", "command": "python3 <仓库>/src/claude_code_hook.py session-start", "timeout": 30}]}],
       "UserPromptSubmit": [{"hooks": [{"type": "command", "command": "python3 <仓库>/src/claude_code_hook.py user-prompt-submit", "timeout": 5}]}]
     }
   }
   ```

   ⚠ 普通 token 让隐藏入口不出现在 Claude Code 的工具列表里，但**这不是安全边界**：两条 token
   都在这份 `env` 里，Claude Code 跑命令时会一起带进去，模型执行一句 `env` 就读得到。hook 和模型
   是同一个系统用户，本来也隔不开。它挡的是模型从工具列表里自己去调；隐藏入口只读，真被绕过，
   最坏是跳过 hook 的预算和去重，不会改记忆库。

4. 验收：新开一个会话，开场上下文里有【最近记忆召回】；再在 `env` 里加
   `"PASSIVE_RECALL_OBSERVATIONS": "<本地 JSONL 路径>"`，发一句和旧记忆相关的话，观测里出现
   `"state": "injected"`；`/mcp` 里 latent 的工具不含 `latent_passive_recall`。然后按上文格式给用户出
   部署报告，当前模式写“历史保留”。

**关闭**：把 `LATENT_PASSIVE_RECALL` 删掉或改成别的值，下一条消息起生效，换窗召回照常。已经写进
对话记录的旧资料不会消失，要干净就新开会话。

## 兼容性记录怎么看

| 分级 | 含义 |
|---|---|
| **维护者复现通过** | 维护者在写明版本、模式和判据的同一条件下复现 |
| **外部实测，维护者未复现** | 外部用户提供实际运行证据，但维护者尚未在同条件复现 |
| **机制／文档推断** | 只确认宿主理论上有入口，尚无 Latent 实际接入证据 |

当前记录：

| 环境 | 分级与结果 | 边界 |
|---|---|---|
| Latent 参考宿主 `reference-host-passive-w5-v1`，Windows、Python 3.12.10 | 维护者开发环境跑通 hook 时序、隐藏入口、候选／组装、临时与历史保留注入、关闭和脱敏观测 | **开发环境，不构成受支持宿主**；参考宿主没有完整聊天产品的保存、恢复、分叉与压缩能力，也不能替真实模型自然效果和成本背书 |
| Claude Code 2.1.283，`UserPromptSubmit` hook（hook 把内容写到 stdout），历史保留模式，事实模式，服务端事实模式首版 | 维护者自用环境真实对话观察 33 回合：递到 28 回合，自然接住 17／28，用错 0，复读 0 | 判据：“接住”＝回话里自然用上、且让回话更像记得对方；“用错”＝用了但说错事实，或把旧状态当成现在。采集条件：维护者自用的云端 Claude Code 环境，一次连续观察。样本小，不代表其他宿主或模型 |

## 怎么反馈

普通问题请使用 GitHub 的“自动浮现问题”Issue 表单；跑通或接入失败的宿主记录请使用“自动浮现
宿主兼容性”表单。必填只有完整 commit、宿主名称与版本、hook 执行时机、当前模式、实际结果
与预期结果。最小虚构复现和脱敏日志有帮助，但不是提交门槛。

**禁止上传真实人格、记忆正文、问句、回答、token、私人路径和原始导出包。** 无法安全提供
内容时只交环境与阶段信息，并注明内容不能公开。跨用户读取、未授权写入、凭证泄露或任意文件
访问属于安全问题，请按根目录 [`SECURITY.md`](../SECURITY.md) 走 GitHub 私密漏洞报告。

初期不承诺响应时间。处理优先级依次为：数据损坏或不可恢复风险、跨用户读取／未授权访问、
凭证问题、错误资料持续进入历史、接入失败、没有浮现或自然效果不理想。

> 所有 Issue 我们都会认真回复；迭代之后会回到原 Issue 告知结果。 跑通了也请告诉我们——成功记录和失败记录一样有用。谢谢每一位愿意反馈的人。
