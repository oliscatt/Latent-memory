# 后台落档

聊天一直在同一个会话里进行，记忆交给后台进程去整理：它隔一阵看一眼对话，攒够了就把这一段整理成当天的记录，写进 Latent。聊天的人不用提醒模型“记一下”，也不用在换窗前手动收尾。

它和模型自己调 `latent_append` 是两条互不排斥的路：

- **模型当场写回**：聊到要紧的事，模型自己判断、自己写。好处是及时，坏处是要靠模型记得，长会话里容易漏。
- **后台落档**：不靠模型自觉，按时间和条数兜底，把整段对话按天收进记忆库。

两条都开时，同一件事可能被写两次（一次是模型当场写的一句，一次是后台按天整理的一段）。这不影响检索，只是库里会多一些重复的说法；嫌重复就只留一条路。

随包的参考实现是 `src/background_archive.py`，只用 Python 标准库。

## 它做什么

1. **读对话**：读 Claude Code 的会话记录（`~/.claude/projects/<项目>/<会话>.jsonl`），或者你自己的前端导出的通用 jsonl。只取双方说出来的话：思考过程、工具调用、工具结果、子代理、后台任务的完成通知，以及自动浮现注入进来的旧记忆，都不算对话。
2. **够了才动**：游标之后的消息按本地自然日切，先处理最老的那一天。满足其中一条才整理：
   - 当天攒够 `--min-messages` 条（默认 60）；
   - 最老的一条已经等了 `--stale-minutes` 分钟（默认 90）；
   - 那一天已经过去（最后一次机会，哪怕只剩一两条也收）；
   - 当天待整理的超过 `--max-chars` 字（默认 30000），先切最老的一段。

   只有一方在说话（比如只有你发了消息、还没有回复）时不动，等对话真正发生。
3. **一次性子进程整理**：默认跑 `claude -p --tools "" --effort low`，**不给任何工具**，素材全在 prompt 里。先写初稿，再对照原始对话自审一遍（主语有没有写反、日期和时段、有没有编造、有没有流水账）。正文用 AI 一方的第一人称，`--me` 和 `--user` 定两边的名字。
4. **形状闸**：输出必须首行是 `# 对话整理 · 日期`，末行是 `当下状态：……`。不合形状就带着纠正提示重来一次，还不合就**不落盘**，游标不动，记一次失败。模型觉得不值得写就回 `PASS`，这是正常出口，不算失败。
5. **写进 Latent**：通过 HTTP 调 `latent_append`，走服务端完整校验，写进去聊天那边的检索和自动浮现立刻看得到。加 `--facts` 时再跑一次事实拆条，一句一条随同一次写回进事实库（部署开了自动浮现事实模式才有用）。
6. **写成功才推进游标**。

## 要求

- Latent 以 Streamable HTTP 常驻（`--http`）。后台进程和聊天的那一端要连同一个服务端；纯 stdio 部署时，服务端不会自己重读别人写进去的记录。
- 一个能从 stdin 读 prompt、往 stdout 写正文的模型命令。默认是 Claude Code 的 `claude -p`，用的是你本机 Claude Code 登录的账号和额度；换成别的命令行也行，只要满足这个输入输出约定。
- 对话来源要能读到。Claude Code 的会话记录在跑 Claude Code 的那台机器上，后台进程也要跑在那台机器上。

## 配置（AI 按下面做）

1. 起服务端（已经按《自动浮现》起过的，跳过这步）：

   ```bash
   python3 src/mcp_server.py --corpus <语料目录> --http 127.0.0.1:8765 --token <普通token>
   ```

2. 找到要落档的会话记录。Claude Code 在 `~/.claude/projects/` 下按项目目录分文件夹，一个会话一个 `.jsonl`。来源写成文件就只读这一个会话，写成目录就读目录下所有会话（恢复会话复制过来的旧消息会去重）：

   ```text
   claude-code:/home/<你>/.claude/projects/<项目目录名>
   ```

   自己写的前端用通用格式，每行一条：

   ```json
   {"ts": "2026-10-19T21:30:00+08:00", "role": "user", "text": "……", "id": "可选的消息 id"}
   ```

   `role` 只认 `user` 和 `assistant`；`ts` 可以是 ISO 时间或 epoch 秒。来源写成 `jsonl:<文件路径>`。

3. 先手动跑一次：

   ```bash
   export LATENT_MCP_URL=http://127.0.0.1:8765/mcp
   export LATENT_MCP_TOKEN=<普通token>
   python3 src/background_archive.py run --source claude-code:<路径> --me <AI 的名字> --user <你的名字>
   ```

   输出一行 JSON：`written`（写进去了，带 `recordId`）、`idle`（还不够门槛）、`pass`（模型判断不值得写）、`failed`（失败，原因在 `error`）。

4. 交给系统常驻，两种选一种：
   - 常驻进程：`python3 src/background_archive.py watch …`，每 `--interval` 秒（默认 600）检查一次；
   - 定时任务：cron 每 10 分钟跑一次 `run …`。

   同一份来源同一时间只会有一个在跑（锁文件），cron 叠上了也不会重复写。

   要马上把游标之后的全部整理掉（比如[《原地续接》](原地续接.md)裁上下文之前），跑 `flush`：不看门槛，一批一批整理到没有为止，模型回 PASS 的那段也越过去。

5. 验收：聊够一段之后跑 `status`，`history` 里有这一段的 `recordId`；再用 `latent_search` 查这段里的一个具体的词，能查到。

## DeepSeek Harness（DSH）会话接入

Android 上的 DSH 0.2.x 将会话保存为 `~/.dsh/sessions/<项目>/<会话>/session.v4.jsonl.zstd`。这是压缩的事件流。后台落档读取的是转换后的 `jsonl:<文件>`。每个会话使用独立、固定的导出路径，让落档游标能接着上次的位置继续。[宿主格式说明](https://github.com/oliscatt/Latent-memory/issues/63)

公仓里附了一份可直接用的导出器：[`examples/host-dsh/dsh_export.py`](../examples/host-dsh/dsh_export.py)——增量游标、注入消息过滤、去重、两种助手消息布局，外加一份虚构夹具与 `tests/dsh_export_test.py`。下面两段是它的最小原理；字段对不上时以它为准。

1. 用 `zstd -dc "$session/session.v4.jsonl.zstd" > "$session/events.tmp"` 解压一个会话。需要系统有 `zstd` 命令；解压失败时保留上次成功的导出文件。
2. 按行读事件。用户消息只收 `user/message` 且 `data.source.kind` 缺省或为 `user` 的记录，助手消息只收 `assistant/message`。从消息的 `content` 数组提取 `type == "text"` 的正文，忽略思考块、工具调用、工具结果、子代理回流和尝试事件。按会话内的 `data.id` 去重，保留消息的原始发送时间。先核对宿主实际时间字段，毫秒 epoch 需除以 1000 转为秒。
   下面以事件顶层 `ts` 为 ISO 时间或 epoch 秒、正文位于 `data.content` 的布局为例。若设备格式不同，先对照一条普通消息调整取值。将脚本保存为 `export_dsh.py`。

   ```python
   import json, sys

   seen = set()
   for line in sys.stdin:
       event = json.loads(line)
       kind = event["type"]
       if kind not in ("user/message", "assistant/message"):
           continue
       data = event["data"]
       if kind == "user/message" and (data.get("source") or {}).get("kind") not in (None, "user"):
           continue
       key = data["id"]
       text = "\n".join(b["text"] for b in data["content"] if b["type"] == "text").strip()
       if not text or key in seen:
           continue
       seen.add(key)
       print(json.dumps({"id": key, "ts": event["ts"], "role": kind.split("/")[0],
                         "text": text}, ensure_ascii=False))
   ```

   ```bash
   zstd -dc "$session/session.v4.jsonl.zstd" > "$session/events.tmp" &&
     python3 export_dsh.py < "$session/events.tmp" > "$session/chat.next" &&
     mv "$session/chat.next" "$session/chat.jsonl"
   ```

3. 写成 UTF-8 JSONL，每条消息一行。比如一次虚构的展签校对会话，转换后应是：

   ```jsonl
   {"id":"u1","ts":"2026-10-31T09:00:00+08:00","role":"user","text":"展签用青铜色。"}
   {"id":"a1","ts":"2026-10-31T09:01:00+08:00","role":"assistant","text":"我把展签定为青铜色。"}
   ```

4. 先写临时文件，确认解压和转换都成功后再替换固定的 `chat.jsonl`。每次重新导出要保留原消息 ID 和时间。沿用上面配置的服务地址、凭证和一次性模型命令，执行：

   ```bash
   python3 src/background_archive.py run --source "jsonl:$session/chat.jsonl" --min-messages 2 --timezone UTC+08:00
   python3 src/background_archive.py status --source "jsonl:$session/chat.jsonl"
   ```

   手机使用自己的整理命令时，设置 `LATENT_ARCHIVE_MODEL_CMD`。用上面有明确决定的样例验收时，确认 `run` 返回 `written`、`status` 的 `history` 中能找到同一 `recordId`，再用 `latent_search` 查“青铜色”。相同导出再次运行应为 `idle`。导出临时文件含有原始事件，转换完可从设备上清理。


## 参数

| 参数 | 环境变量 | 默认 | 说明 |
|---|---|---|---|
| `--url` | `LATENT_MCP_URL` | 必填 | 服务端地址，例如 `http://127.0.0.1:8765/mcp` |
| `--token` | `LATENT_MCP_TOKEN` | 无 | 服务端 `--token` |
| `--source` | `LATENT_ARCHIVE_SOURCE` | 必填 | `claude-code:<文件或目录>` 或 `jsonl:<文件>` |
| `--me` | `LATENT_ARCHIVE_ME` | 我 | AI 一方的名字，正文里的“我” |
| `--user` | `LATENT_ARCHIVE_USER` | 对方 | 对方的名字 |
| `--model-cmd` | `LATENT_ARCHIVE_MODEL_CMD` | `claude -p --tools "" --effort low` | 一次性模型命令 |
| `--state-dir` | `LATENT_ARCHIVE_STATE_DIR` | `~/.cache/latent-archive` | 游标账本和锁文件 |
| `--timezone` | | 东八区 | 按哪个时区切自然日，写法同服务端 `--timezone` |
| `--min-messages` | | 60 | 当天攒够多少条就整理 |
| `--stale-minutes` | | 90 | 最老一条等了多久就整理 |
| `--max-chars` | | 30000 | 一次最多整理多少字 |
| `--no-review` | | 关 | 跳过自审，少一次模型调用 |
| `--facts` | | 关 | 同时拆事实条目 |
| `--timeout` | | 600 | 单次模型调用超时秒数 |
| `--interval` | | 600 | `watch` 的检查间隔秒数 |
| `--notify-cmd` | `LATENT_ARCHIVE_NOTIFY_CMD` | 无 | 连续失败时执行，最后一个参数是提醒文字 |
| `--notify-after` | | 3 | 每连续失败这么多次提醒一次 |

## 不会悄悄丢、不会重复写

- **写成功才推进游标**。模型调用失败、输出不合形状、服务端连不上，游标都不动，下次从同一段重来。
- **失败看得见**：`status` 里有连续失败次数和上一次的错误；配了 `--notify-cmd` 的，连续失败到 `--notify-after` 次就跑一次（比如推手机的命令），之后每满这么多次再提醒一次。
- **PASS 不反复问**：模型对某一段回了 PASS，同一段不会每次检查都再问一遍，等来了新消息再连同新消息一起看。那一天已经过去、或者这是被字数上限截出来的一段时，PASS 之后直接越过。
- **写到一半进程死了**：写进去之前先把这一段的正文存进账本。下次启动发现账本里有没写完的一段，先用正文里的一句话去记忆库查：查到了说明上次其实已经写进去，只推进游标；查不到就用存下的**同一份正文**补写，不重新生成。
- **补写前一天**：记录的日期标签由服务端按写入当天打。整理的是前一天的对话时，正文第一句会写明“这是某天的对话，某天补记”。

## 数据流

整理时，游标之后的那一段对话原文会作为 prompt 交给 `--model-cmd`。默认的 `claude -p` 会把它发到 Anthropic；换成别的模型命令，就发到那个服务。除此之外，后台进程只和你配的 Latent 服务端通信。账本里存的是游标位置、最近 20 次写入的 `recordId`，以及没写完的那一段正文（写完即清空）。

## 关闭

停掉 `watch` 进程或删掉 cron 那一行即可。已经写进记忆库的记录不受影响；要删某一条，用 `latent_cleanup`（需要那条的 `recordId`，`status` 的 `history` 里有最近 20 条）。

## 已知限制

- 只读 Claude Code 会话记录和通用 jsonl 两种来源。别的客户端要先把对话导成通用 jsonl。
- 模型输出靠形状闸挡住开场白和拒绝话术，挡不住“形状对、内容写偏”。自审那一步就是为这个加的，但它也是模型，不是保证。
- “查到了就不补写”是按正文里的一句话去检索对账，不是精确比对；极少数情况下会多写一次，用 `latent_cleanup` 删掉多的那条。
